# Skill 维护清单

用于主路由已经选择维护、评估、分发、默认启用或源码同步的任务。本文件只补充运行中的诊断、迁移和评估；主路径、附加方面、行为合同、来源与动作边界继续由 `SKILL.md` 的主路由和已加载的设计规则决定。本文件完成后返回主流程，不建立另一套标准，也不把失败输出和纠偏过程建成历史案例库。正常生产持续读取的完整示范按运行资源合同维护。

## 1. 先判断维护目标

- 现有行为合同是什么？如果创建时没有写，用用户真实请求和当前规则先还原一份。
- 是触发不准？
- 是流程没执行？
- 是输出风格不稳定？
- 是来源术语、内部字段或过程标签进入了用户成品？
- 是 reference 读太多或读错？
- 是运行成本太高？
- 是已经没人用？
- 是当前职能比用户反复需要的结果更窄，还是比稳定角色更宽？
- 如果目标 Skill 具有自我进化能力，是学习主体、经验拆分、落点或触发条件出了问题，还是经验已经写入却没有被未来请求读取？

维护判断以现有行为合同、真实运行证据和用户结果为依据。

准备修改前先使用主流程的能力台账覆盖全部活动行为和运行资源。维护目标只决定本轮重点，不缩小保全范围；用户这次只指出一个问题，不表示其它未提到能力可以退出。先把纠正落到长度、格式、受众、技术深度、行动方式、主要成品或补充交付等具体方面，只让被点名的方面改变。

维护任务只要把用户结果从一个 Skill、资源、工具、供应商、协议或架构移到另一个目标，就同时属于能力迁移。此时沿用主流程的同一份能力迁移图和统一验证等级；不要把它缩成“补几个文件”“换一个 helper”或“让测试通过”。没有来源到目标的能力转移时，继续按普通维护处理，不增加迁移步骤。

## 2. 当前任务中的行为核对

先按本次实际改动和验收主张选择证据。只改路由、触发、停止位置或输出文字合同时，用代表性请求检查真实路径；新增互斥分支、扩大触发范围或容易误触发时，再增加相邻边界请求。创作类修改默认检查指令、参考输入和上下文组合，不完整跑一条真实请求；只有明确验收成品效果且更低强度证据不足时，才生成最小必要样例。

运行验证命令前先把本次主张映射到改动位置和实际消费者，并选出最低充分检查。验证深度只在这条受影响链内升级；全量入口、仓库共置、重要文件名称和发布动作不能代替消费者证据。目标检查没有出现跨边界故障时，在当前消费者处停止。

隔离会话与相邻边界请求不是同一级动作。只有用户明确要求，或必须证明结果不依赖当前会话、错误代价足以支持额外成本且没有更低强度办法时，才使用隔离会话；确有必要时优先使用产品内受控子 Agent。用户可见的新任务只按用户明确要求创建，外部 CLI 只在 CLI、协议或命令行兼容性本身是验证对象时使用。复用现有上游产物和项目根目录，不重复解压、下载或准备来源。

核对时只记录会改变判断的内容：

```text
用户怎么问：
应该触发吗：
第一步应该做什么：
允许读取和执行什么：
输出骨架：
本次明确改变的方面：
继续沿用的现有用户可见结果：
停止条件：
用户可观察的通过标准：
主路径及其选择依据：
每个阶段的前置输入、中间产物、生产者、消费者、副作用和验证对象：
由这些依赖推导出的实际次序：
同一方面的唯一判断位置与优先顺序：
```

具备真实调用条件时检查真实读取、工具动作和最终输出；当前只能依据规则判断时明确标为推演。请求原文、输出、报告和工作区只用于当前核对。

### 2.1 将行为诊断收口为决定

用户询问某次 Skill 为什么走错、应该怎么修，或指出回答只承认错误却没有给方案时，诊断不能停在责任归因。先根据真实规则、调用位置和用户可见结果作出且只作出下面一种结论：

- **需要修复**：规则缺失、彼此冲突、优先顺序错误、位于消费者不会读取的位置、下层覆盖了上层决定，或旧路径仍在生效。回答必须写清未来正确行为、唯一判断位置、受影响文件与调用点、一次性迁移方式和验证链；已获写入授权时继续实现，未获授权时停在明确方案与确认边界。
- **无需持久修复**：活动规则已经在正确的唯一位置精确覆盖该请求，真实链路也能稳定消费；问题是本次执行没有遵循规则，且没有证据表明路由、条件或验证存在结构缺口。回答必须说明不修改的证据和理由，并立即给出这次本应得到的正确结果或下一步，不能只说“偶发错误”。
- **目前无法判断**：现有证据不足以区分执行偏差和持久缺陷。回答必须点明缺少的规则、运行输出或调用证据，以及拿到证据后如何在前两类之间判定；不能把不确定性伪装成无需修复。

用户可见回答默认使用“结论；证据与根因；正确行为；最终修法或不修改的理由；影响范围与唯一所有者；验证方式与当前停止位置”这一顺序。格式可以自然合并，但六项决定不能被“我做错了”、经验总结或责任解释替代。发现需要修复时，先修最早能够唯一决定行为的位置，再迁移所有消费者并退出冲突旧路径；不要在事后输出层追加同义提醒。

## 3. 先做行为保真审计

准备删除、合并、移动或压缩规则前，先标出会改变执行行为的内容：

- 第一判断和处理顺序。
- 必要追问和缺失信息处理。
- 失败条件与降级动作。
- 输出协议和质量门槛。
- 来源语言、内部工作语言与最终用户语言的转换位置。
- 路由、资源读取和脚本调用条件。
- 每个独立结果的主路径，以及各附加方面的判断顺序。
- 每个选择点所需证据由哪个前序阶段产生，消费者是否晚于生产者，验证失败返回哪个生产阶段。
- 下层资源完成后返回主流程的位置。
- 能在问题发生前主动走对的判断机制。

这些内容逐项对应回能力台账。模板、完整示范、脚本、schema、索引和资产不能只按文件计数；同一文件里的不同触发条件或输出合同分别登记。

同时使用主路由已经加载的约束清洗规则扫描限制性指令。临时记录每条规则保护的用户结果、正向合同覆盖情况和四级处理结果。一般能力提醒、抽象品质要求、反向重复和案例残留优先退出；有效目标进入正向合同；权限、范围和强度进入条件边界；硬禁止通过完整保留门槛后留在实际决策点。

来自外部材料的候选先沿 `absorption-and-governance.md` 得出“具体细节已经存在、只有大方向、值得吸收的新细节、不吸收”四种结论；维护活动规则时再标记最少够用的状态：

- **具体处理已具备**：不查看来源也能识别同一条件、保留同一必要细节并作出同一处理；机器资源还须由活动入口和消费者实际使用，之后才能收敛重复表述。
- **只有大方向**：只有上位方法或同类结果，仍缺少会改变观察、选择、内容或验收的条件与细节。
- **冲突**：两个位置要求不同，需要确定保留哪一个。
- **路由冲突**：同一结果存在多个主路径，或同一方面存在多个生效判断，需要回到共同上层确定唯一结果。
- **应移动**：规则有用，但不在实际会读取的位置。
- **用户明确退出**：用户已经明确不再需要该能力或结果，可以在完成仓库要求的处置后退出。
- **待确认**：新架构不再使用，但用户没有要求退出，继续保留活动能力或在会改变结果时确认，不能按“过时”处理。
- **行为误删风险**：删除后会少做一个判断、追问、降级或检查，必须先等效合并或移动。

只有具体处理已经具备的重复表达，或用户明确退出的能力，才能离开活动路径。收敛前先接通唯一真源的全部适用请求；机器资源还要接通调用点和消费者并验证。移动规则时同时迁移所有调用点，不保留旧入口或兼容解释。文件删除继续服从当前仓库的授权规则。

维护任务涉及退出供应商、模型、工具、脚本、框架或旧入口时，使用主流程已经加载的吸收规则建立载体处置矩阵。检查范围覆盖外部依赖、领域判断、模板、schema、传输合同、消费者、校验和恢复机制。共处一个文件、类或调用栈的项目分别判断，保留项迁入最终架构并接通消费者，明确退出项保持退出。

当材料包含运行问题或连续纠偏时，只在当前任务中按时间顺序定位最早失效判断，再区分根因是主路径选错、附加方面漏选、同一方面存在冲突判断、下层改写了上层合同、规则缺失、规则已经存在但未执行、规则放错层级、条件变化后没有重判，还是旧路径仍在生效。规则已经存在但未执行时，优先修正 `SKILL.md` 的唯一判断位置和读取条件；不保存事件过程，也不新增同义规则。

维护自我进化型 Skill 时，先核对其顶层路由是否把普通领域任务和学习结果分开，并明确学习主体、最终真源和正式消费者。目标 Skill 学习时，稳定机制应进入它自身会被未来请求读取的活动行为；项目事实保留在项目真源；独立共享资源需要用户明确结果和持续消费者。随后把一段材料中的多项成功经验、失败、纠偏和稳定约束分别通过价值门槛，并检查高频、严重、容易误诊或依赖特定条件的重要问题是否保留了识别与处理所需的构成性细节。

这项维护先完整拆分独立结果；含失败、纠偏、保护拦截、绕行或残留时先确定主要原因及独立次级结果，再提取有效机制中会改变未来结果的来源细节。随后逐项比较目标能否独立作出同一具体处理，之后才提炼共同机制和可叠加特殊维度、判断持久化价值与历史责任。目标 Skill 当时未启用只说明历史失败不能归因于它，不得提前截断经验提取；“具体处理已具备”不能只凭相似文字、上位方法或 reference 可达。

同时检查正常使用中哪些结果被明确认可、重复选择、真实验证或在后续任务中自然依赖。把相邻需求按共同用户结果归并，判断它们是否构成当前 Skill 应承担的上层角色；用户没有提出异议、没有再次使用或历史中没有出现某项能力都不是充分证据。

同时检查行为合同是否准确承接用户最终结果。合同出现范围扩张或角色压缩时，回到职能边界和行为合同，重新确定默认来源、动作、输出和停止条件，再迁移执行步骤。

## 4. 修改策略

- 触发不准：改 `description`，用本次代表性请求确认；新增相邻边界时再补一个边界请求。
- 用户本意被改写：先改行为合同，再一次性迁移 `SKILL.md`、reference 和所有活动入口。
- 职能过窄或过宽：先根据明确结果、重复使用、可观察成功、排除和误触发确定上层角色，再一次性迁移 `description`、主流程、reference 路由、输出和停止条件；能力范围与动作权限分别处理。
- 流程没执行：改 `SKILL.md` 的主流程。
- 关键规则被忽略：把规则上提到 `SKILL.md`。
- 主路径选错：按独立用户结果重写 `SKILL.md` 的主路径选择。
- 子类型交叉：把任务或产物子类型的互斥条件收回 `SKILL.md` 同一判断点；输出合同不同的模板保持独立入口。
- 附加方面漏选：在主路径之后补齐信息来源、动作权限、方法强度、输出或停止条件的判断。
- 同一方面冲突：在共同上层确定唯一判断位置和优先顺序，一次性迁移所有调用点。
- 链路次序错误：回到阶段前置、中间产物、生产者、消费者、副作用和验证对象，重新推导顺序；不把判断机械前移或后移，也不让上游约束污染下游成品。
- reference 读错：改 `SKILL.md` 里的路径、读取条件、行为目的和返回位置。
- 自我进化落点错误：回到 `SKILL.md` 的学习落点合同，先确定目标 Skill、当前项目或独立共享资源中的唯一主体，再一次性迁移规则、资源和消费者；不能用资源目录反向替代这个判断。
- 输出不稳定：补输出顺序或最终清单。
- 技术语境或内部字段污染成品：在最早的内容选择与成文位置分开来源语言、工作语言和用户语言；模板保留信息职责，最终输出写行动者、动作、可观察变化和结果。
- 校验不清：先改通过标准，再改 skill。
- 提示词污染或过度防御：先沿正式调用点冻结实际提示词输入，让治理解释、检索标注和候选分析停在上游，只把当前事实、任务、必要格式、经选择的参考与固定协议交给生产消费者；再补足正向合同并完成约束分级，不建立禁词表或统一删减有效输入。
- 验证范围膨胀：回到验收主张、改动位置和实际消费者，保留最低充分检查；只有出现新的受影响消费者证据时才扩大，不用全量入口证明局部修改。
- 能力迁移不完整：回到主流程的能力迁移图，补齐来源活动链、目标真实运行前提、正式生产者、边界、消费者和用户结果；按实际达到的验证等级报告，不能用临时夹具或结构测试抬高完成表述。

## 5. 每次修改后检查

- 代表性请求是否仍按用户本意通过？
- 是否引入新的误触发？
- 代表性请求的实际输出是否符合行为合同，而不只是触发和第一步正确？
- 反馈或纠偏是否只改变了用户点名的方面，未被点名的主要成品和补充交付是否仍然存在？
- 是否把主要成品、用户可见的补充交付和内部过程正确分开，没有因为内容位于正文之后就误判为内部过程？
- 删除、降级或改为按需提供现有用户可见结果时，是否有对应的明确依据；若用户此前未直接要求，是否作为单独决定展示并明确确认，而不是混入整体方案？
- 是否扩大了默认信息来源、工具动作或输出范围？
- 当前职能是否覆盖用户反复需要的完整结果，同时没有把无共同目标的能力堆进来？
- 缩小是否有明确排除、持续冲突或职责迁移等积极证据，而不是只因为没有使用记录？
- 是否在达到用户结果后按停止条件结束？
- 是否让 `SKILL.md` 变胖但没有新增动作？
- 是否把默认规则错误地写进 reference？
- 每个独立结果是否只有一条主路径，附加方面是否按固定顺序组合？
- 多阶段顺序是否由真实依赖推导，每个路由选择点是否已经取得区分证据，成品验证是否发生在成品产生之后并返回生产阶段？
- 同一方面是否只有一个生效判断，互斥条件是否已经在共同上层确定优先顺序？
- 下层资源是否只执行已选职责，并在条件不满足时只报告、停止，没有重选类型、模板或替代路线？
- 所有 reference 是否都由 `SKILL.md` 直接选择，reference 之间是否没有调用、覆盖或重新分流？
- 改造前能力台账中的原位保留项和迁移保留项是否仍有活动入口、消费者与可观察结果？
- 修改前适用于共同入口的规则是否仍覆盖相同适用请求和正式消费者，没有被缩进较窄分支？
- 被删除或移动的行为是否已经等效覆盖，是否出现行为误删风险？
- 目标载体是否已经退出，迁移保留项是否通过正式生产与消费链产生可观察结果，明确退出项是否没有被兼容或恢复逻辑带回？
- 能力迁移的每项完成表述是否与结构可达、真实实例化或端到端消费的实际证据一致？
- 是否没有保存失败样本、回归案例、纠正故事、案例提示词、输出或工作区？
- 实际生产提示词中的每项内容是否都有正式消费者和职责，治理解释与候选分析是否只交付选择结果，没有进入生成模型的候选空间？
- 每条验证命令是否直接覆盖本次改动或必须成立的发布边界；证据深度是否只在受影响消费者内升级，没有把仓库全量入口当作默认验收？
- 是否完成了当前任务中的临时行为核对，并准确区分推演与实际运行？
- 限制性语句是否全部完成分级，正向合同是否独立驱动正常请求，保留的硬禁止是否都能说明触发范围和实质后果？
- 已核实但与目标用户无关的信息是否留在内部，来源实现说法和内部字段是否经过语义转换后才进入成品？
- 必要术语是否保留精度并连接当前情境，一次性案例成句和纠偏措辞是否都留在当前任务，正常生产需要的完整示范是否仍由明确消费者直接读取？
- 影响目标长期行为的核心原则是否已经转成具体规则，过程性原则是否已经由 Meta-skills 实际执行？
- 自我进化型 Skill 是否只在学习结果成立时进入修改路径，多项经验是否分别改变了明确行为，项目事实与独立共享资源是否仍停在各自边界？

## 6. 保留运行资源，不保留治理轨迹

维护结论写入会改变未来判断的通用规则、确定性结构检查和正常生产链真实消费的运行资源。用户请求、纠正过程、临时自然语言输入输出、运行报告和临时工作区在完成当前任务后不进入 Skill。若项目因合规或运维另有日志要求，日志属于项目自己的受控系统，Meta-skill 不把它吸收为教学材料。

## 7. 下线或合并

出现这些情况，考虑收窄、合并或删除：

- 长期无人使用。
- 和其它 skill 边界重叠。
- 经常误触发且难以收紧。
- 只有通用知识，没有真实流程或团队偏好。
- 维护成本超过收益。

这些信号需要结合明确角色和真实使用判断，单独的沉默或暂时未使用不足以删除能力。下线前先搜索引用，确认没有其它流程仍指向它。

搜索不到引用只说明当前路由可能断裂，不证明能力无价值。先回到能力台账核对触发条件、用户结果和历史消费者；只有完全等价能力已经接管，或用户明确要求退出，才执行下线或合并。

## 8. 本地默认启用与源码同步

当用户要让一个持续维护的 Skill 取代功能重叠的系统 Skill 时，把正在修改的源码目录作为唯一真源，用文件系统联接接入 Codex。后续修改只发生在源码目录，联接负责即时同步。

### 8.1 确认真实边界

1. 确认源码目录包含最终 `SKILL.md`，先从源码目录运行 `scripts/quick_validate.py`。
2. 检查当前机器实际使用的 Codex 用户目录、配置文件和系统 Skill 路径。用户级 Skill 默认安装在 `$HOME/.agents/skills`；配置文件通常位于 `$CODEX_HOME/config.toml`，未设置 `CODEX_HOME` 时位于 `$HOME/.codex/config.toml`。
3. 检查用户目录和旧 Codex 目录中是否已有同名文件、目录或失效联接。Codex 不会合并同名 Skill；进入下一步前必须确定唯一活动入口。
4. 读取目标 Skill 的 `description` 和 `agents/openai.yaml`。隐式调用需要 description 覆盖真实请求，同时 `policy.allow_implicit_invocation` 为 `true` 或保持缺省。

### 8.2 建立唯一活动入口

1. 目标位置固定为 `$HOME/.agents/skills/<skill-name>`，联接目标固定为持续维护的源码目录。
2. 目标已存在且不是正确联接时先停止。需要删除时取得用户明确许可；不删除时，把旧入口移到 Skill 扫描目录之外的归档位置，再确认原位置空闲。
3. Windows 使用目录联接，POSIX 使用符号链接。创建后读取联接目标，确认它精确指向源码目录，而不是旧副本、父目录或中间同步目录。
4. 从联接路径重新读取 `SKILL.md`，比较源码路径与联接路径的文件哈希，并从联接路径再次运行校验器。三项都一致才算接入成功。

Windows 目录联接的命令结构：

```powershell
New-Item -ItemType Junction -Path "$HOME/.agents/skills/<skill-name>" -Target "<source-skill-folder>"
```

POSIX 符号链接的命令结构：

```bash
ln -s "<source-skill-folder>" "$HOME/.agents/skills/<skill-name>"
```

### 8.3 禁用重叠的系统 Skill

先解析系统 Skill 的真实 `SKILL.md` 绝对路径，再在 Codex 配置中添加精确路径规则：

```toml
[[skills.config]]
path = "<absolute-system-skill-path>/SKILL.md"
enabled = false
```

Codex 会把同名 Skill 保持为独立入口。替代流程保留新 Skill 自己的稳定名称，并按真实绝对路径禁用被替代项，使选择器中只保留目标入口。

写入后解析整个 TOML，确认语法有效、目标条目只有一个且 `enabled` 为 `false`。修改全局配置后重启 Codex；当前线程已有的 Skill 列表不会反向刷新，必须在重启后的新任务中检查。

### 8.4 验收默认调用与持续同步

按以下顺序验收：

1. 在新任务的 Skill 列表中确认新 Skill 可见，被禁用的系统 Skill 不再作为活动入口。
2. 使用一个符合新 Skill description 的正常请求，确认 Codex 隐式选择新 Skill；需要确定调用时使用 `$<skill-name>` 显式验证。
3. 修改源码目录中的一个无行为风险字段，确认联接路径立即读到同一内容；若产品界面未刷新，重启 Codex后再查，不创建第二份副本。
4. 再次运行源码与联接路径校验，确认后续维护始终发生在唯一源码目录。

最终交付说明源码真源、活动联接、被禁用项、是否需要重启，以及结构检查和新任务行为检查各自的结果。达到这些结果后停止，不继续修改系统自带文件。

## 9. 完成目标 Skill 的仓库发布

主路由已经确认创建、改造或迭代目标 Skill，且用户没有选择只改本地时，发布是同一结果的默认完成阶段，不在本地验证后再次请求相同的提交或推送授权。

先从目标 Skill 的实际目录取得准确 Git 根、当前分支、upstream、远端默认分支和远端 HEAD。发布候选从本轮确认的行为合同开始，按文件或内容片段映射到正式消费者，再求出让本轮结果独立成立的获准改动依赖闭包；已有工作区修改、其它任务、来源不明文件和未获准删除不自动进入候选。闭包依赖未获准改动或无法与旧改动安全分离时，在暂存前准确报告依赖并停止。

对最终候选运行与受影响结果相称的检查，确认最后一次相关修改之后证据仍然新鲜，再按准确路径或内容片段暂存。检查暂存差异只包含获准闭包后创建提交，推送到已经配置的 upstream，并重新读取远端 HEAD 核对它与本地提交一致。当前分支相对远端分叉、认证失败、分支保护拒绝或远端在发布期间变化时保持现状并报告阻塞；不创建远端、不改变可见性、不强制推送，也不把整个脏工作树改称完整结果。

交付按下面的固定结果骨架说明实际状态：

```text
目标 Skill 与准确仓库根：
本轮获准发布范围：
验证结果：
提交 SHA 与分支：
推送结果与远端 HEAD：
仍留在本地且未发布的修改：
未完成边界或恢复办法：
```

只有目标 Skill 的活动文件、正式消费者和验证结果已经进入该远端提交，且远端 HEAD 已核对，才报告本轮 Skill 迭代与发布完成。没有 Git 仓库、没有现有远端或缺少授权时，准确停在本地已验证或发布受阻，不把本地完成概括成已经推送。
