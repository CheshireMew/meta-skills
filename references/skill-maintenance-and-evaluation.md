# 维护、评估和持续使用一个 Skill

用于复杂维护、旧版本比较、顽固问题验收、本机默认启用、源码同步和仓库发布。本说明补充实际做法，不重新定义目标 Skill 的工作。

## 1. 先判断问题发生在哪一层

先看真实请求和真实结果。触发错误、材料没有读到、用户意思被改写、整体职能不合适和程序链路断开，属于长期缺陷；一句话多余、局部节奏不顺或一次执行没有遵循已有规则，先直接修本次结果。

创作成品要完整读完，并与用户实际保留或最小修改后的版本比较。少量删改后主体选材、事实关系和推进仍成立，不修改写作架构；只有不同成品反复出现整体失败，才回到上游。

一次诊断最后只给出三种结论：需要修改、无需长期修改、证据不足。未经保持其它输入不变的比较，原因只能称为待验证猜想，不能写成已经找到的根因。需要修改时说明哪项用户结果会变好、哪个活动机制有证据造成问题、准备怎样替换以及怎样核对；不能停在责任解释或新增提醒。

## 2. 分清能力和历史脚手架

保留的是目标 Skill 能完成的真实请求、必要材料、工具、权限和用户结果，也包括用户原话或已批准方案明确确定的目的、材料边界、资源职责、系统路由和输出约定。现有步骤、路由名称、测试断言和文件布局是调查证据，不自动成为用户决定；更简单的实现完整承接结果和明确决定后可以替换。

用户没有提到某项真实能力，不等于允许删除。当前没有调用的位置也要先查是否曾被旧改造切断。但下列内容应当作为历史堆积收回：同义提醒、旧入口和恢复逻辑；没有实际使用者的字段、日志或检查；把开放判断做成计数、评分和采用证明；把一次成品瑕疵升级成所有请求的前置步骤。

旧版本更好时，找到最后一个正常版本，读取当时真正参与结果的主文件、材料和工具。比较用户拿到的结果和材料怎样进入工作，只恢复本次明确要找回的价值；同一提交中相邻的旧默认、旧目的、旧路由、旧资源分工和旧输出不能顺带回流。

## 3. 理解用户是在举例还是限定范围

用户列举若干问题，并用“比如”“等等”“不光这些”或一个概括性原则说明共同现象时，检查所有活动位置是否存在同一问题。用户明确说“只改这一处”“仅限以下项目”时，才把清单当成边界。不能因为维护规则要求控制范围，就把用户用来说明问题的例子误当成完整需求。

## 4. 用替换完成修复

在真正产生错误的规则、材料交接、模板或脚本处改成正确做法，并一次迁移直接使用位置。上层已经正确时修覆盖它的下层；模板持续生成旧结构时修模板；校验器强制旧格式时修校验器。相同意思不在多个文件重复写，旧实现不以兼容或兜底名义留下。

新增、删除或改变系统选择、条件分支、路由、多候选、评审、二次细化、自动回退或多阶段处理，或者改变用户已经明确确定的做法时，必须在方案中说明差异并获批。一份确认覆盖方案内的实现调整、测试迁移和失败后的定点修正；只有新增用户可见行为、改变方案外的明确决定、权限或必要材料时回到确认点。

Meta-skills 自身的方法和目标 Skill 都要修改时，先完成并冻结 Meta-skills 的版本，再用这个固定版本处理目标；不能同时改变维护方法和被维护对象后归因结果。

## 5. 用正常请求和重复采样评估

文字和普通 Skill 修改使用一个表面不同的正常请求，检查是否正确理解用户表达的共同问题，是否保留真实能力和必要材料，是否清除了旧实现，以及最终结果是否可用。创作看实际成品并以用户阅读判断为准；研究核对来源；程序产物用同一份真实输出经过正式生成和读取；外部动作核对权限、目标和结果。

模型结果存在明显随机性时，不用一次成功或失败代替结论。比较前固定用户原始请求或用户确认的交接、必要材料、完整参考、模型与设置、代码版本和运行方式，只改变待验证因素；任一项无法证明相同，这轮比较无效。准备一组覆盖主要正常场景的代表性请求，修改前后重复运行，并保留没有参与调试的请求。人工先用成对比较校准什么算更好，再记录：单次生成的合格率 `single@1`；多个候选中至少有一个合格结果的比例 `pass@N`；评审实际选中合格候选的比例 `critic@N`；二次细化后相对入选稿的改善或退化。一起记录事实错误、延迟和成本。

这些数据用于定位问题，不自动增加流程。候选里已有好结果但评审选不中，检查评审；候选里没有好结果，检查生成输入或参考；二次细化经常变差，就取消细化。同一因果猜想连续两次受控核对仍不能解释结果时，停止据此修改并报告证据不足；不得换一种措辞继续追加规则。只有证据表明单次生成不足，而且用户批准新的选择或多阶段机制后，才把多候选和评审加入目标 Skill。

同一问题反复出现、过去曾宣称修好却再次出现，或者当前对话已经给出答案暗示时，先在当前任务内做最低成本的充分核对：阅读真实结果和活动差异，运行直接覆盖改动的目标检查；只有静态检查无法证明行为时才补一个正常请求。重复和答案暗示只说明可能存在上下文污染，不自动要求全新独立任务。

只有用户明确要求，或当前结论确实依赖排除对话暗示、低成本检查无法回答，并且独立验收已经写入获批方案时，才使用全新独立任务。它只收到用户原始请求或确认交接、必要原始材料和可证明的代码版本，不继承当前对话、诊断、失败输出、期望答案或验收标准；父任务摘要不能冒充原始请求。实际使用时始终串行，完整结束前不开第二个。新鲜上下文只证明没有继承当前对话，不能证明修改导致结果变化；需要比较效果时仍要固定其它输入，不能证明输入与代码版本时结果无效。

结构检查、真实材料读取、程序链路、单次合格率、候选覆盖、评审选择和最终用户结果分别如实报告。一个通过不能代替另一个。

## 6. 收窄、合并或下线

用户明确退出、持续误触发、另一项能力已经完整接管，或长期维护成本明显高于实际价值时，可以收窄或合并。先让保留的用户结果由新做法完整接住，再移开旧入口；文件删除继续遵守仓库授权。

## 7. 在本机默认启用并保持源码同步

用户要求持续维护的源码目录取代重叠系统 Skill 时，以源码目录为唯一修改位置，并用文件系统联接接入 Codex。开始前确认源码 `SKILL.md` 通过结构检查，查清当前 Codex 用户目录、配置文件、已有同名入口和目标 Skill 的界面信息。

用户级入口通常是 `$HOME/.agents/skills/<skill-name>`。目标位置已经存在且不是正确联接时停止；需要删除先取得许可，不删除时把旧入口移到 Skill 扫描范围之外的归档位置。

Windows 使用目录联接：

```powershell
New-Item -ItemType Junction -Path "$HOME/.agents/skills/<skill-name>" -Target "<source-skill-folder>"
```

POSIX 使用符号链接：

```bash
ln -s "<source-skill-folder>" "$HOME/.agents/skills/<skill-name>"
```

创建后重新读取联接目标和 `SKILL.md`，比较源码与联接路径的文件哈希，并从联接路径再运行结构检查。需要禁用重叠系统 Skill 时，先取得它真实 `SKILL.md` 绝对路径，再在 Codex 配置中写入准确条目：

```toml
[[skills.config]]
path = "<absolute-system-skill-path>/SKILL.md"
enabled = false
```

解析完整 TOML 确认有效后重启 Codex，在新任务中检查新 Skill 可见、旧入口不再活动，并用正常请求确认默认选择。最后验证源码改动能够立即从联接路径读到；不要创建第二份副本。

## 8. 完成目标 Skill 的仓库发布

目标 Skill 已有 Git 仓库，并且已经配置要推送到哪个 GitHub 仓库和分支，而且用户没有选择只改本地时，发布仍是创建、改造或迭代的默认完成阶段，不在本地核对后重复请求相同的提交和推送授权。

先取得准确仓库根、当前分支、当前跟踪的远端分支和远端最新提交。只选择让本轮用户结果完整成立的已授权改动；已有工作区修改、其它任务、来源不明文件和未获准删除不自动进入提交。无法与其它改动安全分离时，在暂存前说明并停止。

运行与本次结果直接相关的最终检查，确认它发生在最后一次修改之后。按准确文件或内容片段暂存，复核暂存差异只包含本轮范围，再提交、推送当前跟踪分支，并重新读取远端最新提交确认与本地一致。

分支已经分叉、认证失败、分支保护拒绝或远端在发布期间变化时保持现状并报告；不创建远端、不改变可见性、不强制推送，也不夹带整个工作区。

用户明确要求公开的一行安装时，推送前用本地路径运行 `npx skills add <local-path> --list`，推送后用仓库地址再运行一次，确认只发现预期 Skill。仓库只有一个 Skill 时给出 `npx skills add <owner>/<repo>`；多个时用 `@<skill-name>` 指定。目录收录、Release 和实际隔离安装是另外的要求，不自动增加。

最终直接说明本轮发布范围、实际检查、提交与分支、推送和远端核对结果，以及仍留在本地的修改。只有远端最新提交已经包含活动文件和本轮结果，才说发布完成。
