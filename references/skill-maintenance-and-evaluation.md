# 维护、评估和持续使用一个 Skill

用于复杂维护、旧版本比较、顽固问题核对、本机默认启用、源码同步和仓库发布。主入口已经确定授权和停止边界；这里仅说明复杂维护怎样取得证据、实施一次替换并保存真实状态。

## 1. 冻结当前问题和基线

完整读取真实请求、完整结果、活动文件、当前差异和必要历史。触发错误、材料没有读到、用户意思被改写、整体职能不合适和程序链路断开，属于长期缺陷；一句话多余、局部节奏不顺或一次执行没有遵循已有规则，先直接修本次结果。

已有未提交修改是当前真实状态和需要保护的工作，不是缩小调查范围或拒绝修改的理由。调查仍读取所有相关活动文件、当前差异和必要历史；实施前区分本轮目标与已有工作，把能够辨认的修改精确合并。只有同一目标区域的意图仍无法分清、继续写入会真实覆盖已有工作时才停止。发布时不再尝试把本轮修改与此前本地工作拆开；用户没有选择只改本地时，整个工作区作为一个提交范围共同验证和发布。

实际结果与用户真正采用、保留或局部调整后的结果一起检查。少量局部处理后主要结果和关键关系仍成立，不修改 Skill 架构；开放创作再结合主体选材、事实关系和推进是否仍然成立判断。一次诊断只得出三种状态：需要修改、无需长期修改、证据不足；没有固定其它输入的比较时，原因只能称为待验证猜想。

获批前记录准确基线：目标文件现状、相关差异、必要材料、运行入口和准备验证的主要修复依据。旧版本更好时，读取最后一个正常版本及当时真正参与结果的资源，只恢复用户明确要找回的结果，不带回相邻旧默认、旧路由和旧资源分工。

## 2. 区分能力和历史脚手架

保留目标 Skill 能完成的真实请求、必要材料、工具、权限、用户结果和已批准决定。步骤、路由名称、测试断言和文件布局只是调查证据；更简单的实现完整承接结果后可以替换。

用户没有提到某项真实能力，不等于允许删除；当前没有入口时先检查是否曾被旧改造切断。同义提醒、旧入口和恢复逻辑、没有使用者的字段与日志、把开放判断变成计数或采用证明的机制，以及由一次成品瑕疵产生的长期前置步骤，都不作为能力保留。

## 3. 只实施获批的那一次替换

在真正产生错误的规则、材料交接、模板或脚本处完成替换，并一次迁移直接使用位置。上层已经正确时修覆盖它的下层；模板持续生成旧结构时修模板；校验器强制旧格式时修校验器。旧实现不以兼容或兜底名义留下。

语法、格式、断链和与方案一致的测试实现错误可以直接修正。若实施中需要改变主要修复依据、用户结果、必要输入或材料边界、路由或阶段、活动资源、文件范围、验收方法或权限，停止目标写入；这些变化属于下一份方案，不在本轮换一种说法继续追加规则。

Meta-skills 自身和目标 Skill 都要修改时，先完成并冻结 Meta-skills 的版本，再用该固定版本处理目标，不能同时改变维护方法和被维护对象后互相证明有效。

## 4. 让核对成本服从结论

普通修改先阅读最终差异、直接引用和用户可见结果，再运行覆盖本次改动的最低成本检查。能够客观核实的结果，用真实产物、状态和证据判断；允许多种结果成立、体验取决于用户偏好的结果，在用户判断前中性展示完整结果和可观察差异。测试数量、字段齐全、步骤完成、参考痕迹和其它维护指标不能代替最终结果。只核对实际结果中已经出现的事实错误、硬要求违反或其它具体问题，不把尚未发生的风险预先写成运行限制。研究核对来源，程序让同一份真实产物经过正式生成和读取，外部动作核对权限、目标和结果；开放创作中由现有材料合理支持的用途、含义或表达延伸属于正常判断。

只有用户明确要求评估稳定性，或者结论本身涉及概率、方案优劣或多候选机制时，才进行受控重复采样。比较前固定原始请求或确认交接、必要材料、完整参考、模型与设置、代码版本和运行方式，只改变待验证因素；无法证明这些相同时，不声称因果。确实需要量化时再记录 `single@1`、`pass@N`、`critic@N`、细化后的改善或退化、事实错误、延迟和成本，这些数据不自动授权增加正式流程。

全新独立任务只在用户明确要求，或获批方案确实需要排除当前对话时使用，并通过当前 Agent 宿主提供的原生隔离任务机制创建。在 Codex App 中，当前任务内的独立核对使用子代理；只有用户明确要求创建任务列表中可见的新任务时，才使用分支会话树。任务本身运行在 Agent CLI 中时，沿用该宿主的原生会话机制。独立任务只收到用户原始请求或确认交接、必要原始材料和可证明的代码版本，不接收诊断、旧输出、期望答案或验收标准；始终串行运行。新鲜上下文只证明对话隔离，不证明修改有效。

依赖用户偏好的结果只有在用户判断失败，或者存在能够直接核实的问题时，才进入失败停止；用户尚未判断时保持中性候选状态并交回用户。能够客观核实的结果按相应证据判断。真实结果验收失败后保留准确输出、差异和基线状态，立即停止目标写入。未通过的候选不得发布、设为默认、宣称完成或用另一项结果掩盖；下一步需要新的用户决定。

## 5. 收窄、合并或下线

用户明确退出、持续误触发、另一项能力已经完整接管，或长期维护成本明显高于实际价值时，可以收窄或合并。先让保留的用户结果由新做法完整接住，再移开旧入口；文件删除继续遵守仓库授权。

## 6. 在本机默认启用并保持源码同步

用户要求持续维护的源码目录取代重叠系统 Skill 时，以源码目录为唯一修改位置，并用文件系统联接接入 Codex。开始前确认源码 `SKILL.md` 通过结构检查，查清当前 Codex 用户目录、配置文件、已有同名入口和目标 Skill 的界面信息。

用户级入口通常是 `$HOME/.agents/skills/<skill-name>`。目标位置已经存在且不是正确联接时停止；需要删除先取得许可，不删除时把旧入口移到 Skill 扫描范围之外的归档位置。

Windows 使用目录联接：

```powershell
New-Item -ItemType Junction -Path "$HOME/.agents/skills/<skill-name>" -Target "<source-skill-folder>"
```

POSIX 使用符号链接：

```bash
ln -s "<source-skill-folder>" "$HOME/.agents/skills/<skill-name>"
```

创建后重新读取联接目标和 `SKILL.md`，比较源码与联接路径的文件哈希，并从联接路径再运行结构检查。需要禁用重叠系统 Skill 时，先取得它真实 `SKILL.md` 绝对路径，再在 Codex 配置中写入准确条目：

```toml
[[skills.config]]
path = "<absolute-system-skill-path>/SKILL.md"
enabled = false
```

解析完整 TOML 确认有效后重启 Codex，在新任务中检查新 Skill 可见、旧入口不再活动，并用正常请求确认默认选择。最后验证源码改动能够立即从联接路径读到；不要创建第二份副本。

## 7. 完成目标 Skill 的仓库发布

目标 Skill 已有 Git 仓库，并且已经配置要推送到哪个 GitHub 仓库和分支，而且用户没有选择只改本地时，发布仍是创建、改造或迭代的默认完成阶段，不在本地核对后重复请求相同的提交和推送授权。

先取得准确仓库根、当前分支、当前跟踪的远端分支和远端最新提交，并读取完整工作区状态与差异。发布范围固定为该仓库当前全部本地改动，包括已跟踪修改、未跟踪文件和已经存在的删除；不按任务、来源、文件或内容片段选择性排除，也不因工作区不干净停止。用户明确选择只改本地时整个仓库都不提交，不能把它解释成只留下其中一部分。

根据整个工作区的实际影响范围运行最终检查，确认它发生在最后一次修改之后。使用 `git add -A` 暂存全部修改，复核暂存状态与暂存差异覆盖提交前看到的全部已跟踪修改、未跟踪文件和删除，没有漏项，再提交、推送当前跟踪分支，并重新读取远端最新提交确认与本地一致。检查失败或任何一项不能进入同一提交时保留完整工作区并停止，不退回部分提交。

分支已经分叉、认证失败、分支保护拒绝或远端在发布期间变化时保持现状并报告；不创建远端、不改变可见性、不强制推送，也不拆分工作区绕过阻塞。

用户明确要求公开的一行安装时，推送前用本地路径运行 `npx skills add <local-path> --list`，推送后用仓库地址再运行一次，确认只发现预期 Skill。仓库只有一个 Skill 时给出 `npx skills add <owner>/<repo>`；多个时用 `@<skill-name>` 指定。目录收录、Release 和实际隔离安装是另外的要求，不自动增加。

最终直接说明整个工作区的发布范围、实际检查、提交与分支、推送和远端核对结果。只有远端最新提交已经包含提交前的全部本地改动、提交后工作区没有遗漏，而且远端与本地一致，才说发布完成。
