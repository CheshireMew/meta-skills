# 维护、评估和持续使用一个 Skill

用于复杂维护、长期评估、本机默认启用、源码同步和仓库发布。主文件已经决定本次用户结果和路径；本说明只补充对应做法，不重新分流。

## 1. 先说清到底哪里不好用

根据真实请求和当前规则，说明问题属于哪一类：触发错了、用户意思被改写、步骤没有执行、参考材料读错、最终文字难懂、结果不稳定、检查过重、长期资源没有被实际使用，还是 Skill 的职能过宽或过窄。

用户只指出一个问题时，只改变这个方面。准备修改前仍要盘清其它活动能力和长期资源，防止局部纠正顺手取消原有结果。

如果本次把用户结果从一个 Skill、工具、供应商、协议或旧结构搬到另一个位置，同时按能力迁移处理；不能把它缩成复制几个文件或让测试通过。

## 2. 分辨有效机制和历史堆积

有效机制应当有明确用户结果、正常请求真的会经过、会独立改变判断或成品，并且移除后存在具体损失。用户明确认可、反复选择、实际使用结果或稳定规范能够支持它。

下面这些现象通常说明问题已经层层加码：

- 同一判断在主文件、参考说明、模板和检查器中换词重复；
- 每次出错只在最后增加提醒、禁令、兜底或恢复逻辑，没有修最早的错误决定；
- 为开放判断增加候选数量、评分、状态、登记和采用证明；
- 字段、日志、索引或检查没有正常使用者；
- 检查只证明过程执行过，却被用来声称用户结果有效；
- 少数高风险情况的重流程常驻普通请求。

当前没有调用的位置先检查是否因旧改造断开，不能直接判成废物。确有完整等价做法接管，或者用户明确要求退出后，才收回旧入口。迁移完成后不保留兼容层和隐藏恢复逻辑。

## 3. 把诊断收口成一个决定

一次诊断最终只能落在三种结论之一：

- **需要修改**：规则缺失、冲突、顺序错误、放在不会读取的位置，下层覆盖主文件决定，特殊材料常驻普通路径，检查早于对象产生，或者旧流程仍在生效。说明未来正确行为、真正决定它的位置、直接受影响的文件和怎样核对；已有修改授权时继续实施。
- **不需要长期修改**：现有活动规则已经准确覆盖，真实路径也能使用，只是本次执行没有遵循。说明证据和不改文件的理由，并直接给出这次本应得到的正确结果或下一步。
- **证据不足**：无法区分一次执行偏差和长期缺陷。说明缺少哪条规则、运行结果或使用证据，以及拿到后怎样判断。

不能停在“我做错了”、责任解释或经验总结。需要修改时，修最早能作出正确决定的位置，并同步移开冲突旧做法；不要只在最终回答阶段追加提醒。

## 4. 根据问题修改唯一位置

- 触发范围不准：修改 `description`，用一个正常请求和必要的相邻请求核对。
- 用户本意被改写：先恢复用户原话和结果，再同步修改主文件、直接参与的参考说明和模板。
- 整体职能过窄或过宽：根据明确结果、反复使用、真实成功、排除和误触发重新确定角色；动作权限另行处理。
- 主要步骤没执行：修改 `SKILL.md` 的正常流程。
- 关键规则埋得太深：把真正改变默认行为的判断上提到主文件，详细方法仍留在对应说明。
- 两条路径争夺同一结果：由主文件确定唯一选择，迁移所有使用位置。
- 可以同时成立的要求被写成互斥分支：先选主要结果，再依次加入来源、权限、深度和输出要求。
- 参考说明读错：修改主文件中的读取条件和顺序；参考说明不自行改路线。
- 只要求通俗却改变内容：恢复事实、关系、详略、主次、确定程度和材料作用，只重写难懂说法。
- 提示词被内部过程污染：把设计理由、检索标签、候选分析和成品后检查移回各自位置，只把当前执行所需内容交给它。
- 检查范围膨胀：回到本次结果和实际使用位置，保留能证明它的最少检查；出现新的受影响范围后才扩大。
- 能力迁移不完整：补齐真实材料、正式入口、实际使用步骤和用户结果，按真正完成程度报告。

同一决定改完后，所有直接使用位置一次迁移到新规则，旧同义说法和冲突检查一起退出。不能留下两套正常流程。

## 5. 用正常请求评估行为

文字和路径修改使用新的、表面不同的正常请求，检查是否触发正确、第一步是否正确、该读的材料是否真的读到、最终结果是否符合用户本意，以及是否在正确位置停止。只有新增互斥分支或容易误触发时，再加一个相邻请求。

创作类修改先检查实际指令、完整参考和最终成品，不默认启动隔离会话或生成大量样例。研究核对关键来源和推断。程序读取的产物使用同一份真实输出经过正式下一步，不由使用端手写假数据。外部动作核对权限、准确目标和真实结果。

结构检查、正常请求审读、真实资源读取和最终用户结果分别说明。一个通过不能替另一个通过，也不能为了“全量通过”运行无关检查。

## 6. 维护会自我学习的 Skill

先确认普通项目结果和 Skill 学习是两件事。只有用户明确要求学习时，稳定方法才写进目标 Skill 未来会读取的位置；项目事实留在项目，独立共享库需要用户明确要求和长期使用者。

一段材料里的成功做法、失败、纠正和稳定边界分别判断。先找真正原因，再确认目标是否已经能识别同一条件、理解重要细节并作出同样处理。只有相似文字或大方向不能算已具备。

真实有效的做法进入最早会生效的唯一位置；纠正故事、失败输出、临时回答、比较记录和工作区不保存。完整示例、模板、脚本和素材如果正常请求仍会读取，继续作为长期资源维护。

## 7. 收窄、合并或下线

长期不用、持续误触发、与其它 Skill 完全重叠、只有通用知识没有真实做法，或者维护成本明显高于价值，都可以提出收窄或合并。但沉默、暂时未使用和搜索不到引用只说明需要调查，不是退出证据。

先确认原有用户结果是否已被另一项完全等价能力接管。得到用户明确退出后，迁移所有保留项，再移开旧入口。文件删除仍需遵守仓库授权；不能用归档或兼容层让已经退出的行为继续生效。

## 8. 在本机默认启用并保持源码同步

用户要求持续维护的源码目录取代重叠系统 Skill 时，以源码目录为唯一修改位置，并用文件系统联接接入 Codex。开始前确认源码 `SKILL.md` 通过结构检查，查清当前 Codex 用户目录、配置文件、已有同名入口和目标 Skill 的界面信息。

用户级入口通常是 `$HOME/.agents/skills/<skill-name>`。目标位置已经存在且不是正确联接时停止；需要删除先取得许可，不删除时把旧入口移到 Skill 扫描范围之外的归档位置。

Windows 使用目录联接：

```powershell
New-Item -ItemType Junction -Path "$HOME/.agents/skills/<skill-name>" -Target "<source-skill-folder>"
```

POSIX 使用符号链接：

```bash
ln -s "<source-skill-folder>" "$HOME/.agents/skills/<skill-name>"
```

创建后重新读取联接目标和 `SKILL.md`，比较源码与联接路径的文件哈希，并从联接路径再运行结构检查。需要禁用重叠系统 Skill 时，先取得它真实 `SKILL.md` 绝对路径，再在 Codex 配置中写入准确条目：

```toml
[[skills.config]]
path = "<absolute-system-skill-path>/SKILL.md"
enabled = false
```

解析完整 TOML 确认有效后重启 Codex，在新任务中检查新 Skill 可见、旧入口不再活动，并用正常请求确认默认选择。最后验证源码改动能够立即从联接路径读到；不要创建第二份副本。

## 9. 完成目标 Skill 的仓库发布

目标 Skill 已有 Git 仓库，并且已经配置要推送到哪个 GitHub 仓库和分支，而且用户没有选择只改本地时，发布仍是创建、改造或迭代的默认完成阶段，不在本地核对后重复请求相同的提交和推送授权。

先取得准确仓库根、当前分支、当前跟踪的远端分支和远端最新提交。只选择让本轮用户结果完整成立的已授权改动；已有工作区修改、其它任务、来源不明文件和未获准删除不自动进入提交。无法与其它改动安全分离时，在暂存前说明并停止。

运行与本次结果直接相关的最终检查，确认它发生在最后一次修改之后。按准确文件或内容片段暂存，复核暂存差异只包含本轮范围，再提交、推送当前跟踪分支，并重新读取远端最新提交确认与本地一致。

分支已经分叉、认证失败、分支保护拒绝或远端在发布期间变化时保持现状并报告；不创建远端、不改变可见性、不强制推送，也不夹带整个工作区。

用户明确要求公开的一行安装时，推送前用本地路径运行 `npx skills add <local-path> --list`，推送后用仓库地址再运行一次，确认只发现预期 Skill。仓库只有一个 Skill 时给出 `npx skills add <owner>/<repo>`；多个时用 `@<skill-name>` 指定。目录收录、Release 和实际隔离安装是另外的要求，不自动增加。

最终直接说明本轮发布范围、实际检查、提交与分支、推送和远端核对结果，以及仍留在本地的修改。只有远端最新提交已经包含活动文件和本轮结果，才说发布完成。
