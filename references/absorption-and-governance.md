# 从经验中吸收真正有用的能力

只有用户明确要求目标 Skill 学习、吸收、内化或改进未来行为时使用本说明。目标不是保存历史，而是让未来遇到同类请求时主动做对。

新经验不能覆盖现有价值。开始前先按主流程盘清目标 Skill 当前能做什么、哪些长期资源确实参与；新做法只改造对应问题，不能因为新的分类、更短的文件或一次成功经验让其它能力失去入口。

## 1. 先确定谁要学习

同一份材料可能产生三种不同结果：

- **目标 Skill 学习**：稳定做法写进它以后处理同类请求时真的会读取的位置。
- **当前项目沉淀**：事实、决定和项目经验留在项目自己的材料里，完成后不自动修改 Skill。
- **独立共享资源**：只有用户明确要求跨 Skill 共用，而且已经存在长期使用者时才建立。

“这次任务做完”不等于“修改 Skill”。两者都被要求时，先完成并检查项目结果，再从真实结果中提炼未来做法。

## 2. 按用户结果拆开经验

一段对话或一个项目可以同时包含成功做法、失败、用户纠正、稳定边界和仍待验证的猜想。按它们分别服务的用户结果拆开，不要用一个宽泛结论覆盖全部材料。

对每项经验只需要说明：发生了什么，为什么有效或为什么失败，用户或实际结果怎样证明，未来最早可以在哪个判断位置复用，以及它会改变哪项具体行为。

遇到失败和连续纠正时，先分清表面现象、真正导致结果走偏的判断、临时绕行和遗留问题。优先修正最早有足够信息且仍能控制结果的位置。不能因为某个症状最醒目，就把它升级成所有请求都要经过的新流程。

## 3. 分辨真实有效与层层加码

一项做法值得长期保留，通常同时具备这些证据：

- 它服务明确的用户结果，而不是只让内部过程看起来完整；
- 正常请求确实会经过并使用它；
- 它会独立改变判断、动作、权限、成品或实际风险；
- 移除后会出现可以说明的损失；
- 用户明确认可、反复选择、真实使用结果或稳定规范能够支持它。

下面这些现象优先视为层层加码，需要收回到真正的问题位置：

- 一次错误后，在多个文件不断追加同义提醒、反面禁令和恢复逻辑；
- 把本来可以直接判断的事情改成候选计数、评分、状态、登记或采用证明；
- 字段、记录、索引或检查结果没有正常工作中的实际使用者；
- 检查只证明步骤执行过，却被用来声称用户结果有效；
- 只服务少数特殊情况的重流程常驻所有请求；
- 新规则只是换词复述已有原则，没有改变未来动作。

暂时没有被读取的内容不能立即判成无用。先检查它原本服务什么结果、是否在旧改造中丢了入口，以及是否已有完整等价能力接管。入口断裂时先恢复或迁移；只有完全重复或用户明确退出时才离开活动路径。

## 4. 判断目标是否真的已经具备

暂时不看来源，只读目标 Skill，检查它能否：认出同一条件，知道这个细节为什么重要，并据此作出同样的选择、写出同类内容或完成同类检查。三项都能做到，而且正常路径真的会读取相应规则或材料，才算已经具备。

只有相似词、上位原则或大方向时，要明确说“只有大方向”；不能为了避免修改就写成已经覆盖。目标缺少且有足够证据的内容才吸收；只属于当前案例、证据不可靠或不会改变未来结果的内容不吸收。

## 5. 提炼方法，不保存故事

能放回现有唯一规则的位置，就直接强化那条规则并移开旧说法。只有确实出现一项新的用户能力，而且现有位置无法承接时，才增加最小的新入口和正常使用位置。

失败和纠正主要帮助发现：以后要观察什么、怎样区分情况、做什么、怎样检查以及在哪里停止。人名、项目名称、一次性数字、原回答和纠正过程不进入长期规则。

用户只纠正长度、格式、受众、技术深度、行动方式、主要成品或补充交付中的一个方面时，只改变这一方面。没有修改的部分既不能当成长期认可，也不能当成允许删除。

如果用户保留了事实和关系，只替换了难懂名称、例子或组织方式，应吸收“来源负责支撑事实，最终呈现由当前用户和受众决定”这一职责，不保存这次具体替换，也不机械恢复来源表面措辞。

## 6. 同时提炼共同做法和必要差异

先用日常语言说明这项经验让用户得到了什么、为什么成立。拿掉来源名称、原句、一次性数字和只有原案例才有的说法，再用两个表面明显不同、但仍属于目标范围的对象代入；如果两者都能自然得到同类结果，留下共同做法。如果代入后必须假定新对象具有原案例才有的内容，说明规则仍然太窄，不能冒充共同做法。

同一项经验可以同时包含共同做法和条件差异。共同做法写进所有适用请求都会经过、而且所需信息已经出现的最早位置；会改变识别、判断、动作、产物、验收或停止位置的条件和细节写进相应条件位置。由目标 `SKILL.md` 排定“先走共同路径，再检查本次成立的条件差异，然后组合动作并验收”的顺序；多个条件差异可以同时生效，两层不能互相代替。没有实际做法差异时不虚构特殊情况。

完整示例中的内容分三类判断：

- 删除后能力仍然成立的偶然细节，只属于来源案例；
- 具体取值会随当前请求变化的参数，保留选择方法，不固定数值；
- 删除后会漏认情况、选错方法或明显损害结果的关键结构，保留在相应条件下。

多个完整示例可以共同进入创作上下文。保留它们的全文、来源和选择条件，不用摘要标签代替全文，也不要求证明采用了哪一个。脚本、模板、固定格式和素材如果直接参与产生价值，就随能力一起保留其实际使用位置，不能压成一句抽象原则。

来源方法存在不同精度、成本或风险等级时，先选择能够完整产生用户当前结果的最低一层，更重的方法只在明确条件下进入，不能把最高强度设成所有请求的默认。

## 7. 迁移完整能力

从另一 Skill、项目、工具或旧载体吸收能力时，迁移的是一次真实请求怎样得到用户结果：入口、必要材料或配置、关键判断、实际动作、交接位置、最后使用者和结果都要接上。

先让目标的新入口和全部使用位置能够接住保留项，再退出被替代做法。不同文件放在一起不代表应当一起退出；同一文件里的外部依赖、专业判断、模板、固定格式和恢复办法要按用户结果分别处理。用户明确不要的内容不以兼容或兜底名义带回。

文件已经复制只能证明入口可能存在；真实材料被正式入口读取，才能说材料已经接入；正式步骤产出用户可见结果后，才能说能力迁移完成。不能用临时样本、假配置或消费端手写结果抬高完成表述。

## 8. 最后核对

- 学习主体和写入位置是否明确；普通项目是否没有被擅自升级成 Skill 学习？
- 每项经验是否服务明确结果，并且有真实价值证据？
- 真正有效的能力是否保留，重复提醒、无使用者字段和只证明过程的检查是否退出？
- 当前未使用的内容是否先检查了断路，而不是直接当作废物？
- 共同做法是否换成两个表面不同但仍在范围内的对象后依然自然成立？
- 会改变处理方式的条件差异是否与共同做法同时保留，并分别进入共享位置和条件位置？
- 关键结构、可调部分和偶然细节是否分开？
- 新规则是否进入未来真的会读取的位置，同义旧规则是否已经退出？
- 完整示例、模板、脚本和素材是否继续由正常请求使用？
- 最终说法是否与实际达到的入口、真实材料读取和用户结果一致？

完成稳定做法的写入和对应核对后停止，不保存本次对话、失败输出、比较表或临时工作区。
