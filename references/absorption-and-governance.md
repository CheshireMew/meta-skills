# 吸收可迁移价值与能力

用于从正常成功经验、用户明确认可或反复选择的做法、用户纠偏、旧规则、连续对话、完整项目或外部方法中识别目标 Skill 值得获得的能力，并判断其职能是否过窄或过宽。输入材料只在当前任务中作为证据，不能把案例原文、故事或运行历史复制、改写或换名后写入 Skill。

目标是保留来源材料产生价值的因果链：把已经证明有效的判断前移到正常流程，把边界明确的专业能力放入可选择分支，并让可靠脚本、模板和资产继续承担原本的作用。抽象只删除偶然外壳，不能把专业能力压成任何 Skill 都适用的空泛原则；案例中的具体信息也不能未经判断升级为整个 Skill 的长期默认值。

## 1. 先确定当前目标和值不值得研究

先写清目标 Skill 当前为用户创造什么价值、仍缺少什么，再检查每条候选信息：

- 会不会改变 agent 下次的第一判断？
- 会不会改变处理顺序、方法选择或默认输出？
- 会不会改变通过标准或实际风险？
- 会不会让 agent 少问、少绕、少写废话？
- 会不会让目标 Skill 稳定处理一类此前不会、做不稳或结果明显较差的请求？
- 它是否是来源结果成立所必需的判断、专业知识、操作结构、脚本、模板或资产？

如果答案都是否，不研究也不写入。能被核实不等于值得核实。

正常经验优先寻找这些高信号证据：用户明确说明为什么接受某种结果；同一方法被重复选择或在后续任务中自然沿用；结果经过真实链路、用户使用或其它可观察标准验证；多项相邻需求持续指向同一个上层职能；或者存在独立事实、项目规则与成熟方法支持。

以下只能提出待验证假设：用户没有修改、没有回复或没有反对；某次输出表面完整；孤立提示词或单段描述只出现一次；只因为领域惯例看起来更专业。一个完整项目中的规则、实现、资源和现有产物如果能相互说明某项能力怎样产生，可以证明这项限定能力确实存在，但不能自动证明它应成为目标 Skill 的全局默认。

临时价值记录统一使用 `SKILL.md` 第 3 步。本文件额外确认两点：被接受的是哪项决定或流程，而不只是最终文本；它解决的是一次内容，还是目标 Skill 应稳定承担的职能。

命名史、发明史、人物评价、传播轶事和原案例争议默认跳过。只有用户明确要求，或这些信息会影响证据可靠性、版权、许可证、责任归属时才核查。

输入包含用户修订稿、前后版本或连续纠偏时，可以在当前任务中比较差异：

- 用户删掉、补上、降级或重排了什么。
- 这些变化修正了哪个具体失败。
- 变化影响的是操作结构、判断机制、输出边界还是个人偏好。
- 哪些变化只适用于当前任务，哪些能够迁移。

用户明确修改的地方是高信号证据；没有修改的地方不自动视为长期认可。比较结果只用于定位判断问题，不保存差异记录，也不把最终文本复制成规则。

材料包含失败或纠偏时，按时间顺序找到最早可预防节点，按 `SKILL.md` 的行为合同字段还原问题发生前的正常请求。历史材料只用来定位有效机制、缺失判断、价值因果链和职能边界；正常经验要让未来请求主动复用有效能力，纠偏经验要让用户不指出旧问题时也不会重犯。

## 2. 判断职能边界

把历史中的需求按用户最终结果分组，而不是按页面、文件、工具或用户随口说出的功能名计数。多项相邻能力共同服务同一结果、共享第一判断与信息真源并形成稳定专业角色时，可以建议扩大职能；它们需要不同目标、来源、权限和停止条件时，保留为按需分支或独立 Skill。

建议缩小职能必须有积极证据：用户明确排除、持续误触发、与稳定角色冲突、长期造成错误默认行为、职责已经迁移，或用户确认不再需要。历史中没有出现某项能力、用户一次没有使用或当前请求较窄，都不能单独证明应该删除。

范围变化前形成临时判断：

```text
当前 Skill 承诺的职能：
历史反映的上层用户结果：
建议保持、扩大或缩小：
属于同一角色的能力维度：
仍应按需触发或单独授权的动作：
明确排除与相邻 Skill 边界：
证据强度、反证和关键假设：
```

证据足够时把完整定位作为一个行为合同请用户确认，不逐项索要许可。职能扩大不改变联网、运行、安装、写入、发送、发布和删除的权限边界；这些动作仍按目标 Skill 的任务风险单独定义。

## 3. 通过价值保留与抽象门槛

`SKILL.md` 第 3 步是价值记录、证据门槛、反事实检查和跨表层核对的唯一主规则。本文件只补充吸收判断中容易混淆的四件事：

- 能力身份由什么结果和构成性结构决定，不能只由来源名称决定；
- 独立依据能证明限定能力存在，但不能自动把它升级为全局默认；
- 默认能力、限定能力和需要单独授权的动作必须分开；
- script、模板、schema 或资产如果参与产生价值，要随能力一起迁移到明确消费者，不能只留下文字概括。

来源能力存在不同精度、覆盖、成本、时效或风险层级时，把层级视为可调参数，不把来源的最高强度设为统一默认。临时写清：

```text
用户当前需要观察到的结果：
能够完整产生该结果的最低能力层级：
该层级必须保留的判断、步骤、资源和验收：
更高层级多出的成本与价值：
升级条件：
```

较低层级仍要保留自身成立所需的完整因果链；“降低强度”不能成为删掉关键步骤后交付近似结果的借口。无法通过 `SKILL.md` 第 3 步任一门槛时，只完成当前请求，不做长期吸收。

## 4. 迁移要求

具体落盘位置、正向流程格式、案例隔离和资源验证等级使用主流程已经加载的设计规则。吸收任务只增加以下要求：

- 限定能力的选择条件留在 `SKILL.md`，过重的完整方法才进入 reference；
- 参与价值因果链的 script、模板、schema 与资产保留职责和消费者，不把它们降成一句原则；
- 单次事实、临时偏好、故事、失败样本和不改变动作的空话不迁移；
- 被替代规则一次性迁移到唯一真源，不保留旧入口或同义解释；
- 正向流程离开原案例仍能说明触发、动作、通过和停止，临时核对材料不进入 Skill。

## 5. 最终检查

- 目标 Skill 的价值缺口是否先于来源材料确定？
- 限定能力是否有独立依据，默认化是否另有足够证据或用户确认？
- 偶然细节、可调参数和构成性细节是否分开，来源的强度层级是否没有被压成一个最高默认？
- 迁移后是否新增或强化可观察能力，而不是增加同义原则？
- 必要 script、模板、schema 和资产是否保留明确消费者，并按实际条件报告验证等级？
- 职能扩大是否形成连贯角色，缩小是否有积极证据，动作权限是否仍单独控制？
- `SKILL.md` 是否保留选择条件和主流程，reference 是否只承载过重方法或限定能力？
- 最终是否仍通过主流程指定的质量清单，且没有保存临时请求、输出或工作区？
