# 设计 Skill 会长期使用的资料和文件

只有正常请求会反复读取某份资料、模板、脚本、素材、私人库或固定数据时使用本说明。先看它怎样帮助用户得到结果，再决定保存形式；不能因为文件是 JSON、Markdown 或放在某个目录，就替它发明一套管理流程。

## 1. 先分清普通参考和机器资源

写作案例、钩子和风格参考通常只需要完整正文、来源信息和帮助查找的少量标签。可以分类存放，但使用时可以把多个相关全文一起交给模型综合。标签只帮助找到内容，不限定只能学习哪些方面，也不要求逐项证明采用。

资源能否共享正文、索引或候选集合，服从目标 Skill 已经确定的职责边界。不同资源已经被规定为独立或互斥时，不能因为内容相似就复用同一条目、互相替代或合并索引；准备改变这种边界或选择条件时，先说明修改前后差异并取得用户同意。

只有程序必须解析固定字段，资源需要跨任务按稳定名称查找、独立更新，或者实验必须锁定输入、版本、顺序和运行记录时，才属于机器资源。此时才需要固定格式、版本、登记入口和从新项目读取的检查。普通文本参考不自动承担这些成本。

## 2. 先说清它为什么存在

创建资源前，用普通话回答：它解决什么生产问题，谁维护，正常请求中的谁会读取，根据什么条件选择，读取后改变什么动作或成品，以及用到哪里停止。

没有正常使用者，或者读取后不会改变任何结果的文件，不进入活动资源。当前看不到使用位置时，先检查旧改造是否切断了入口，不能仅凭“没人引用”判定无用。

常见资源及其合适位置：

| 实际作用 | 合适形式 |
| --- | --- |
| 改变触发、判断、权限、输出或停止位置 | 主文件中的规则 |
| 提供一套较长的方法或知识 | 参考说明 |
| 直接填入内容并形成同类成品 | 模板 |
| 展示完整组织、节奏、交互或表达方法 | 完整示例 |
| 由程序解析固定字段 | 固定数据格式 |
| 重复、确定且手写容易错的操作 | 脚本 |
| 直接进入成品或运行环境 | 素材 |
| 从大量内容中找到候选 | 索引；正文仍只有一份 |

同一文件格式可以承担不同作用，一个原文也可以服务多个使用场景，但目标 Skill 已经明确要求相互独立的资源除外。按真实作用和既有约定区分，不按扩展名和目录名区分。

## 3. 让约束强度跟着用途走

程序要读取的产物，应明确实际读取的字段、类型、必填条件、允许值、版本和错误处理。允许自然组织的文章、提示词或创作模板，只固定用户明确要求和真正不能变化的协议；身份、内容取舍、顺序、段落数和表达由当前任务决定。

完整示例要保留正式使用者需要阅读的全文。需要近距离适配时，先分清使示例成立的关系、顺序、节奏和动作，以及只属于那次内容的数量、名称、数值和装饰。前者按当前任务尽量承接，后者由当前输入决定，除非用户要求或固定协议证明不能改变。

会由模型或维护者完整读取的文本资源，每个文件都服从 9,000 tokens 的外层工具预算。一个完整示例、固定协议或具有独立身份的第三方正文不能被摘要冒充；单体内容确实不可拆时，保留原始资源身份，并提供不会把它误报成可整份读取的稳定消费方式。普通方法和可组合资料则按唯一主题拆成多个直接可达文件，不通过压缩语义换取长度合规。

脚本承担确定、重复且结果必须一致的操作。CLI、API、GUI、插件或 SDK 只说明怎样访问背后的能力：普通工具 CLI 可以调用确定性程序，Codex CLI 这类 Agent CLI 则提供模型判断和工具协调。需要固定输入、按哈希核对内容、锁定代码版本和运行顺序或保存可复现记录时，由确定性程序通过合适入口完成；需要隔离模型上下文时，使用当前 Agent 宿主的原生任务机制。在 Codex App 当前任务内使用子代理，只有用户明确要求创建任务列表中可见的新任务时才使用分支会话树；任务本身运行在 Agent CLI 中时，沿用该宿主的原生会话机制。需要理解上下文、审美或专业判断的部分由相应模型、Agent 或专业工具完成。

实验使用的路径、哈希、代码版本、模型设置和诊断记录留在运行清单，不进入创作模型读取的交接内容。Skill 只负责识别意图、调用稳定入口和展示用户结果；程序负责确定性边界。

素材记录可靠来源、许可、格式和正常使用位置。只有最终成品或运行过程确实会读取时，才进入活动 Skill。

索引只保存查找和选择所需的最少信息，并始终指向唯一正文。分类字段来自实际选择问题；容易取得但不改变选择的属性，不升级成主要分类。

## 4. 分清资源当前处于什么状态

真正需要登记的机器资源可以经历三个状态：

- **临时材料**：只解释本次发生了什么，例如诊断报告、截图、试算和临时项目；不进入正式列表。
- **待采用资源**：已经可能有复用价值，但来源、许可、格式、版本、使用条件或正常使用者还不完整；不参与默认生产。
- **正式资源**：来源和使用条件清楚，有稳定名称、版本、唯一正文、正式入口和正常使用者，并能从新的运行项目按名称读取。

状态必须通过明确采用动作改变，不能由目录位置、文件名、一次成功或检查脚本自动推断。“可以使用”和“默认使用”也是两件事；成为默认需要用户确认或稳定产品约定。

## 5. 接通从创建到使用的完整过程

每项活动资源都要能回答：可靠内容从哪里来，谁创建或更新，唯一正文在哪里，如何找到，谁读取，以及怎样进入用户结果。

资源创建者还要保证每个活动文本产物在写入时即可通过文件预算，不能等到下一次维护才整理。拆分后的正文仍各有明确所有者和选择条件；索引只负责查找，不能取代被拆分的完整内容。

字段存在但没人读取、脚本返回结果但下一步不用、模板存在但正式入口绕过，都不算接通。职责变化必须先进入获批方案；实施时同时调整创建者、正文、索引和所有使用位置。新过程接通前不退出旧入口，完成后不保留第二套冲突做法。

源码、运行项目、缓存和任务产物承担不同职责：

- Skill 源码保存长期规则、方法、脚本和随 Skill 分发的只读资源；
- 运行项目保存某次用户任务的可变输入、状态和输出；生成型 Skill 的运行项目属于该 Skill，不属于调用它时碰巧所在的仓库；
- 缓存保存可以从正式输入重新生成的中间结果；
- 诊断证据和任务产物不会因为放在仓库附近就自动成为长期资源。

创建或修改一个会写文件的 Skill 时，先逐个列出真正的写入者及默认位置，包括顶层命令、被调用脚本、第三方辅助脚本、下载、日志、QA、缓存、导出和安装步骤，再为每类文件确定唯一归属：

- 随 Skill 分发并由维护者长期更新的规则、脚本、模板和素材属于 Skill 源码，按仓库规则跟踪；
- 该 Skill 生成的制作真源、运行项目、中间文件、预览、报告、渲染和最终成品进入 Skill 目录内已经声明且被 Git 忽略的本地运行区；用户给出外部素材、在另一个仓库调用、当前存在活动 Git 项目或要求后续交付到外部位置，都不改变生产根；
- 只服务这个 Skill、跨任务继续复用但不随源码分发的配置、角色包、运行记录或私人资源也进入 Skill 目录内已经声明且被 Git 忽略的本地位置；只有它本身是独立维护的大型资料库或外部数据时，才由 Skill 内的配置指向独立数据根；
- 用户结果本身是修改已有源码、文档、配置或其它项目文件时，修改属于用户明确要求改变的准确项目；当前目录、活动仓库、输入文件所在项目和“从这里调用”都不能代替这项明确要求；
- 用户明确要求把生成成品交付到外部项目或目录时，先在 Skill 内完成并验证，再只复制点名成品；制作真源、运行项目和已验证成品继续留在 Skill，外部副本不反向成为活动真源；
- 可重新生成的缓存和临时文件进入系统临时目录或归属方已声明的忽略目录，不散落在仓库根；
- 外部产品的安装文件进入该产品的正式目录，并继续遵守相应授权和替换规则。

所有正常入口通过同一个路径解析决定取得这些位置。生成型 Skill 先由代码文件自身位置确定 Skill 根，再进入该 Skill 声明的 Git 忽略运行区；用户路径只表示输入来源或另行获准的交付目标，不参与生产根解析。项目修改型请求从用户明确要求改变的准确项目解析，外部数据与安装目录从各自正式配置解析，缓存进入系统临时目录或归属方忽略目录。不能因为进程从某处启动，就把当前目录、活动仓库或相对路径解析结果当作输出所有权；嵌套脚本不能另设依赖当前目录的回退。

## 6. 处理本机和私人资源

可执行文件、外部产品设置、私人资料库、账户、模型目录和独立数据根目录可能随机器变化。目标 Skill 只保存自己启动工作所需的入口；外部产品自己的模型、账户和设备设置仍由外部产品管理，单个资源的身份和版本仍由资源自己的清单管理，当前任务输入仍留在运行项目。

配置放在哪里先看它控制谁。只要配置控制的是这个 Skill 自身的执行器、任务路线、模型映射、资源入口、路径发现或其它运行行为，配置就留在 Skill 目录内，不因为其中含有本机路径或密钥而搬到用户全局目录、调用方项目或另建的共享配置中心。可迁移且不含私人信息的公共默认配置随 Skill 源码分发；本机绝对路径、密钥和私人设置放在同一 Skill 目录内的本地配置或环境文件，并由该 Skill 的 `.gitignore` 排除。正式入口合并读取这两类配置，示例、文档和初始化命令也指向同一位置。

只有配置真正属于外部产品，而不是在控制当前 Skill，才继续由外部产品自己的正式配置目录维护；Skill 只保存连接它所需的入口。独立资料库和大型数据可以有自己的数据根，但指向它们的 Skill 配置仍留在 Skill 目录内。不能为一个 Skill 单独发明全局配置目录，也不能同时保留 Skill 内配置、环境变量、硬编码路径和目录猜测等多套正式入口。

本机真实路径和私人值不会随 Skill 分发。缺少本地配置时，只停止依赖它的能力，并准确说明缺什么；不能静默选择相似工具或第一个目录后仍声称原能力可用。

示例配置只说明字段和含义，不能被当成当前机器已经就绪。真实配置能够解析只证明入口格式正确；真实路径和内容被正式读取，才证明资源接入；最终步骤用它产生用户结果后，才证明完整能力可用。

## 7. 迁移旧资源

新建资源、采用正式资源、迁移旧格式和最终生产是不同动作。旧格式只由一次迁移入口读取，转换成最终格式并接通所有使用位置后退出；常规运行不长期保留新旧两套入口。

迁移前按用户结果分别判断旧载体中的方法、模板、数据、素材、检查和恢复办法。共处一个文件不代表一起去留；从历史版本恢复一个资源时，也不能把相邻的旧选择条件、旧职责或旧默认一起带回。保留项先接上新位置，用户明确退出项不以兼容或兜底名义回来；文件移动、归档和删除继续遵守仓库权限。

迁移错放产物时，先解析并核对准确源目录和目标目录，确认不会合并或覆盖，再按相对路径、大小和哈希记录迁移前清单。移动后重新生成清单，检查旧目录是否退出、新目录是否完整、文件内部是否残留旧绝对路径，并分别查看原仓库与目标仓库的 Git 状态。已经被原仓库跟踪的运行产物会显示为移除，未跟踪产物则不会；两种状态都要如实说明，不能把 Git 状态干净误当成文件迁移完整。

## 8. 用真实使用结果核对

根据本次实际改变的资源，只检查直接相关的过程：

- 正式创建者能否用真实输入生成内容；
- 索引是否按真正影响选择的属性找到正文；
- 正式使用者是否读取了唯一正文，而不是摘要或临时副本；
- 多个完整参考能否一起进入创作上下文；
- 程序读取的固定产物是否用同一份真实输出走到下一步；
- 本机或私人资源是否从真实配置进入最终结果；
- 正式资源能否从新的外部项目只凭稳定名称读取；
- 没有默认资源时，流程是否清楚停止或进入新建，而不是擅自选择。
- 从一个不相关仓库或目录调用正式入口时，默认产物是否仍进入已声明归属，调用方没有出现意外文件；
- 用户明确点名外部交付目录时，生产是否仍在 Skill 内完成，外部是否只出现点名副本且没有成为新的活动真源；
- 实际输出目录是否符合预期的 Git 跟踪或忽略状态，路径记录和正式读取是否都指向新位置。

目录存在、字段齐全和脚本成功只证明对应结构。不能用虚构案例、临时目录或固定测试样本冒充真实资源接入，也不为自然语言参考增加不需要的登记和测试。
