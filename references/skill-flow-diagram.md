# 画清一个 Skill 怎样工作

用户要求流程图或链路图时使用。图要让人看懂请求怎样进入、什么事实改变路线、谁产生什么中间结果、下一步怎样使用、检查失败回到哪里，以及用户最终得到什么；不能只画目录和文件名。

## 1. 先确定画哪个状态

- 只读解释、审查或单独出图，默认画当前实际状态。
- 修改前的方案图画准备实现的状态，并标明“拟议”。
- 实施后的核对图只画已经进入活动路径的最终状态。
- 用户要求比较时，分别画修改前和修改后，不把两种状态混在一张无标记图里。

用户没有要求保存文件时，直接在回答中给 Mermaid 图。只有明确要求保存或导出时，才写入指定格式。只要求出图不授权修改目标 Skill。

## 2. 从真正生效的内容建立节点

读取活动 `SKILL.md`、界面信息、主文件直接选择的参考说明、脚本、素材、模板、固定数据和实际使用证据。仓库另有规则时一并服从；归档内容只在用户明确点名时读取。

图中至少覆盖：

```text
用户请求和想要的结果
→ 入口和主文件选择
→ 作出选择所需的材料、事实或授权
→ 实际动作和产生中间结果的人或程序
→ 文件、存储或其它交接位置
→ 使用中间结果的下一步
→ 外部影响和权限边界
→ 检查对象、失败返回位置
→ 用户结果和停止位置
```

每个关键节点都应能找到活动来源。规则声明、脚本实现和真实结果不一致时，分别标明“声明”和“实际”。只有 README、目录名或注释声称支持，却没有活动入口和使用位置时，不画成已经接通；证据不足的连接标成“未确认”。

## 3. 先按真实依赖连线

产生中间结果的步骤先于使用它的步骤；区分路线所需的事实出现后才能选择；权限、准确目标和恢复办法先于外部写入；必须看到成品才能做的检查放在成品之后；检查失败回到真正产生问题的步骤。

图中分别让三类关系可见：

- 请求怎样前进、选择和停止；
- 材料和中间结果怎样从产生位置交给使用位置；
- 检查什么、失败回到哪里、通过后交给谁。

主文件负责选择路线；参考说明、脚本和素材只作为已选工作的一部分。发现下层重新分流、使用步骤早于产生步骤、资源没人使用或检查没有返回位置时，把它画成断点并说明影响。

## 4. 生成可读的 Mermaid 图

普通流程使用 `flowchart TD`，横向阶段更容易比较时使用 `flowchart LR`。矩形表示动作，菱形表示真正改变路线的判断，圆角节点表示用户入口、结果或停止位置，圆柱节点表示文件或其它唯一内容来源；虚线用于检查、反馈或未确认连接。

节点使用简短中文和稳定的英文标识。含括号、冒号或长句的标签加引号，不把绝对路径和整段规则塞进节点。

一张图能完整又清楚地展示全部步骤时只画一张。若一个节点吞掉多个阶段或判断、必须省略重要分支和失败返回、连线拥挤难以追踪，或者不同主要路径各自足够复杂，就先画总览，再按出现顺序展开局部图。

总览保留主要路径、关键选择和图间交接点；每个隐藏实质步骤的聚合节点都要有对应局部图。全部图合起来覆盖本次承诺的完整过程。只有用户明确要求快速概览时，才可以省略局部展开。

## 5. 交付

第一段说明图对应当前、拟议还是实施后状态，覆盖哪些真实入口，是否有未确认断点。随后给出图、关键分支和失败返回的普通话说明，以及让用户能找到活动来源的简短对应关系。证据不足的连接说明还缺什么真实输入或运行结果。

最后确认 Mermaid 能渲染，入口能到达用户结果或明确停止位置，外部动作前有权限边界，检查发生在对象产生后，图与实际来源一致。交付后停止，不因画图时发现问题自动修改目标 Skill。
