# 设计或重做一个 Skill

用于新建 Skill、重做整体职能，或者一次改造会影响多个主要能力时。目标是让真实请求稳定得到用户需要的结果，不是把目录和字段填满。

## 1. 先判断是否值得做成 Skill

适合做成 Skill 的事情通常会重复发生，用户会反复解释相同标准，或者少一个关键判断就容易走偏。只需要一次回答、没有长期做法可复用时，直接完成任务，不创建 Skill。

新建前把用户想得到的结果写成一个自然搜索词，运行：

```text
npx skills find "<query>"
```

第一轮没有实质结果时，最多换一个自然同义词。只阅读真正相关候选的活动 `SKILL.md`，然后说明它能否直接满足、只能提供部分参考，还是仍需新建。安装量只能说明关注度，不能代替质量判断；不自动安装，也不因找到相似方案就取消用户明确要求的创建任务。

## 2. 从用户原话确定 Skill 要负责什么

先写清：用户真正想拿到什么，提供了什么材料，允许或拒绝哪些动作，哪些只是设计者觉得“更完整”但用户没有要求。

确定长期职能时，优先看用户明确说明的角色和结果，其次看反复出现的相邻请求、重复选择的做法和真实使用结果。一次成功、一次沉默或“业内通常这样做”只能提出猜想，不能直接扩大默认职能。

多项能力如果共同服务一个稳定结果、共享主要判断和材料，可以归在同一角色下；如果目标、来源、权限或停止位置不同，就保留为不同路径或不同 Skill。缩小职能要有用户明确排除、持续误触发、职责已经迁走等实际依据，不能因为历史中暂时没出现就删掉。

## 3. 改现有 Skill 前盘清能力

查看主文件及它直接选择的参考说明、脚本、模板、示例、素材和真实使用入口。临时记录：

- 什么请求会使用这项能力或资源；
- 用户最终得到什么；
- 哪些内容和工具确实参与；
- 本次原位保留、迁移保留，还是用户明确要求退出。

是否属于独立能力，以用户结果、动作权限、失败风险和必要做法为准，不能按文件、字段、名称或格式判断。一个文件可能承担多项能力，一项能力也可能依赖多个文件。

用户没有提到、文件过长、新结构暂时没有入口或当前搜索不到使用位置，都不构成退出依据。先检查入口是否在旧改造中被切断；保留项的新入口和实际使用位置接通后，才能退出被替代做法。

## 4. 写一份短而完整的未来行为说明

用代表性真实请求说明：

```text
用户会怎样提出请求：
最终要得到什么：
默认读取什么，允许做什么：
正常情况下按什么顺序处理：
哪些条件会真正改变做法：
用户会看到什么，在哪里停止：
```

只有程序必须读取固定产物时，再补字段、格式、由谁生成、由谁读取和失败处理。只有外部写入或高风险动作时，再补权限、准确目标和恢复办法。写作与开放判断不增加候选计数、唯一参考、评分、采用记录或执行证明。

这份说明离开反面清单后，也应当让另一个执行者知道怎样完成正常请求。没有改变实际做法的字段就是噪声。

目标 Skill 需要使用本机程序、私人资料库、账户或会随机器变化的路径时，只确认这些前提由哪里提供、缺少时哪项能力停止；详细配置留给运行资源方法，不能让本机路径扩张成所有 Skill 的默认设施。

## 5. 组织清楚的处理路径

先按用户要得到的独立结果选择主要路径，再在同一路径内选择确实不能同时成立的成品或任务类型。来源、动作权限、处理深度、输出要求等可以同时成立的方面，在主要路径确定后依次加入。

只有差异会改变第一步、所需材料、允许动作、输出或停止位置时才建立分支。常见请求有一条短而完整的默认路径；深入、昂贵或高风险方法在条件成立时加入，不能把最严格流程设成所有请求的默认。

所有路径和资源读取条件由 `SKILL.md` 决定。参考说明、脚本和素材只完成已经选定的职责；它们不能选择其它参考说明、改换模板或覆盖主文件已经确定的结果。多个资源要一起使用时，由主文件写清顺序。

多阶段工作只需按真实依赖排序：材料和授权先于使用，产生结果的步骤先于读取结果的步骤，必须看到成品才能做的检查放在成品之后，检查失败回到真正产生问题的步骤。不要把一种常见顺序写成所有任务都必须遵守的固定流程。

## 6. 把内容放到真正会使用它的位置

`SKILL.md` 保留触发边界、主要路径、必要条件、默认输出、停止位置，以及读取参考说明和运行脚本的条件。过长方法、领域知识、详细清单和完整示例放到由主文件直接选择的参考说明或素材中。

自然语言能稳定表达的判断留在说明里。只有重复、确定、手写容易错而且结果必须一致的解析、转换、排序或检查才写成脚本。只有程序必须解析固定字段时才建立固定数据格式。

完整示例、模板、脚本和素材在正常请求确实会读取时可以长期保留。失败样本、纠正故事、临时提示词、临时回答和本次比较记录不进入活动目录。

主文件必须同时不超过 220 行和 14,000 个字符。超出时，把详细方法移到由主文件直接选择的一层参考说明，并合并重复规则；不能提高上限、拆行规避，也不能为了变短删除能力。

## 7. 写入前只确认真正会改变的事情

用户只要求审查或解释时保持只读。用户已经明确要求创建、改造或修复时，可以直接实施，不重复确认同一授权。

如果方案会改变用户没有要求改变的默认能力、动作权限、材料作用、主要成品、补充交付，或者会删除、降级、改成按需提供，必须单独说清未来行为和影响，再取得同意。用户确认的是自己以后会得到什么，不是目录是否更整齐。

目标已经有 Git 仓库，并且已经配置要推送到哪个 GitHub 仓库和分支时，获准创建或改造也包含把本轮准确改动提交并推送到当前跟踪分支，再核对远端最新提交。用户选择只改本地时停在本地。创建远端、改变可见性、强制推送、删除、改变未经确认的分支和夹带其它修改仍需单独授权。

## 8. 新建 Skill 的顺序

1. 确认名称和上面的未来行为说明。名称使用小写字母、数字和连字符，不超过 64 个字符，目录名与 `name` 一致。
2. 确认目标父目录；用户没有指定时，说明准备使用的默认位置。
3. 准备用户在列表中看到的名称、25–64 字符简述和一条包含 `$skill-name` 的正常示范请求。
4. 运行 `scripts/init_skill.py` 建立最小入口。目标目录已存在时停止，不覆盖。
5. 用最终行为替换占位内容，只在真实材料就绪时创建参考说明、脚本或素材。
6. 运行 `scripts/generate_openai_yaml.py` 生成界面信息。
7. 运行 `scripts/quick_validate.py`，再重新读取最终 `SKILL.md` 和 `agents/openai.yaml`。

## 9. 迁移能力时判断实际完成到哪里

迁移对象是用户能得到的完整能力，不是相似文件。先还原来源中一次真实请求怎样经过规则、实际材料或配置、执行步骤和使用者得到结果，再确定目标怎样承接。

完成程度分三层，用人话如实报告：

1. **入口已经接好**：目标写清触发条件和使用位置，所需文件存在，但还没有真实材料或下游任务证明实际使用。
2. **真实材料已经读到**：正式入口能够读取本次真实配置、案例、数据或账户，下一步也收到它，但还没有形成最终用户结果。
3. **用户结果已经产生**：代表性请求从目标入口出发，使用真实材料经过正式步骤，用户最终能看到或使用结果。

不能用临时样本、消费端手写数据或假使用者把前两层说成第三层。缺少下一层所需的真实条件时，停在已经证明的位置并说明缺什么。

## 10. 按结果核对并交付

结构检查只证明文件和固定格式。文字和处理路径修改要用新的正常请求审读理解、选择、成品和停止位置；创作看实际成品；研究看来源与推断；程序读取的产物用同一份真实输出走完生成和使用；高风险动作核对权限和外部结果。

最后先说新的行为怎样工作和用户怎样使用，再说明关键文件与实际核对。已经配置要推送到哪个 GitHub 仓库和分支，而且用户没有选择只改本地时，完成精确提交、推送和远端核对后再报告发布状态。达到用户要求后停止。
