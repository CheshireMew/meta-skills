# Skill 设计与行为合同

用于新建、重写、更新或审计一个 Skill。目标不是把文件写完整，而是让真实调用产生用户认可的结果。

设计顺序固定为：先写独立成立的正面流程，再写必要边界；先把正确判断放到最早决策点，再考虑检测。历史案例只作为当前任务的定位证据，默认行为来自用户目标、稳定事实和可迁移机制。

## 1. 先判断要不要做成 Skill

- 这件事是否会重复发生？
- 用户是否反复解释相同标准？
- 少一个判断是否容易跑偏？
- 它缺的是流程、判断标准、模板、脚本还是资料路径？
- 如果只是一次性回答，不创建 Skill。

## 2. 从真实请求还原用户本意

先保留用户原话，不先改写成领域术语。分别写出：

- 用户真正想拿到的结果。
- 用户明确给了哪些材料。
- 用户明确允许或禁止哪些动作。
- 哪些只是设计者认为“更专业、更完整”，但用户没有要求。

优先级固定为：

```text
用户明确结果和边界
→ 默认行为
→ 完成任务所需的方法
→ 领域最佳实践
→ 可选的完整性增强
```

后面的内容在前面已经确定的默认范围内发挥作用。仓库级质量原则约束“怎样做好”，用户可见交付继续由用户目标决定。

## 3. 判断职能是否过窄或过宽

当前一句请求首先说明这次要做什么。Skill 的长期职能结合当前可用的对话、用户提供的历史材料、现有定位和真实使用方式判断，重点提取反复出现的最终结果、相邻能力、继续追问、明确接受、明确排除和误触发。

证据强度按以下顺序判断：

1. 用户明确说明期望的上层角色、最终结果或排除边界；
2. 用户反复提出相邻任务、重复选择同一方法，或在后续任务中自然依赖此前能力；
3. 结果经过可观察验收，或者存在当前产品、团队规则与独立方法依据；
4. 单次成功、未修改、未回复和没有反对提供待验证假设；长期职能由更高等级证据决定。

把相邻能力按共同用户结果归并。多项能力共同构成一个稳定专业角色时，建议扩大到这个上层职能并让用户一次确认；各自服务不同结果、改变不同第一判断或需要不同权限的能力保持独立分支或拆成其它 Skill。

职能收缩以明确排除、持续误触发、与目标角色稳定冲突、职责被其它 Skill 接管或用户已经确认角色收敛为依据。历史中没有出现某项能力只说明当前证据不足。

每次范围判断写清：

```text
当前 Skill 实际职能：
历史反映的用户最终结果：
相邻能力为什么属于或不属于同一上层角色：
建议保持、扩大或缩小：
默认能力与按需能力：
明确排除：
信息来源与操作权限是否变化：
证据强度、假设与需要确认的关键分歧：
```

职能范围回答“能处理什么”，动作边界回答“默认可以做什么”。联网、运行、写入、发送、发布或删除权限分别按动作边界确认。证据足够时把完整定位作为一个行为合同让用户确认；关键分歧会改变 Skill 身份、默认来源、操作权限或主要交付时再逐项追问。

## 4. 写行为合同

创建文件计划前，完成以下合同：

```text
代表性真实请求：尽量使用用户这次的原话、附件和上下文
用户最终想得到什么：能从用户视角观察到的结果
当前职能与建议职能：保持、扩大或缩小，以及证据
当前结果最有价值的能力与仍然缺少的能力：用户现在能稳定得到什么、哪类请求仍然做不到或做不稳
来源价值与最小完整能力单元：哪些判断、知识、结构、脚本、模板或资产需要共同迁移
用户明确要求退出的实现、依赖或行为：准确复述对象与边界
退出对象内部承载的独立能力、资源与消费者：按用户结果拆分，不按文件或模块打包
逐项处置矩阵：每项标记迁移保留、明确退出或需要确认，并说明依据
保留能力的新链路：生产者、传输或存储边界、消费者与用户可观察结果
默认信息真源：本地文件、某个应用、某个仓库、用户输入或其它明确来源
默认允许读取什么：文件、页面、资源和 reference 范围
默认允许执行什么：只读检查、联网、运行、安装、写入、发送或其它动作
最早可预防问题的判断点：在什么动作发生前必须确定什么
默认正向流程：用户不需要提醒时也会主动执行的正确步骤
第一步必须做什么：收到请求后的首个判断或动作
默认输出：第一段回答什么，后续按什么顺序展开
来源语言：材料中的专业、实现、组织和宣传说法分别承担什么证据作用
内部工作语言：合同字段、schema、路由、检查标签和过程记录怎样服务执行
最终用户语言：目标用户需要看见哪些事实、动作、变化和结果
公开信息选择：哪些已核实信息会改变用户理解或行动，哪些只留在内部
必要术语：哪些精确名称必须保留，第一次出现时怎样联系当前情境
正向信息、动作、产物、验收与停止合同：离开限制列表仍能独立执行的流程
约束清洗临时结果：删除、正向改写、条件边界和硬禁止
硬禁止保留依据：具体对象、触发范围、实质后果和正向合同不足之处
按需分支：只有用户说出哪些意图时才能进入
停止条件：做到什么立即交付，不再继续研究或扩张
正向通过标准：用户不需要先遭遇错误或提出纠正就能观察到什么
```

通过标准：另一个 Agent 只看正向合同，就能完成正常请求并判断一次真实运行有没有偏离用户本意。

行为合同中的“默认”是用户没有补充说明时的稳定工作流程。全局默认来自稳定目标和可迁移机制；某项专业能力成立所需的人物、对象、动作、场景、风格、措辞和数值作为构成性结构保留在对应按需分支、reference、script 或 asset 中，并写清选择条件与可调参数。

### 退出实现时拆分能力载体

供应商、模型、工具、脚本、框架、旧入口和文件都是实现载体。退出其中一个载体前，逐项盘点它承载的外部依赖、领域判断、模板、schema、传输合同、消费者、校验和恢复机制。处置由用户明确结果与能力价值决定，文件共置、共同导出或同一调用链不能替代逐项判断。

先为迁移保留项建立最终位置和完整消费链，再切换全部调用点并退出旧载体。明确退出项不进入新架构。存在会改变用户结果的未决项时，在修改前确认；已经明确的处置直接执行。

## 5. 找出会改变方法的分支

只有会改变第一步、来源、动作、输出或停止条件的差异才建立分支，例如：

- 本地文件与远程 URL；
- 快速解释与实际运行验证；
- 可运行程序与提示词、模板、配置合集；
- 只读分析与允许写入；
- 默认回答与用户明确要求的详细报告。

只有会改变第一步、来源、动作、输出或停止条件的差异才建立分支。默认路径独立完整，深入要求留在对应分支。

### 能力存在强度层级时

来源方法或目标结果存在不同精度、覆盖、成本、时效或风险等级时，不把最严格流程直接设为统一默认。先确定用户需要观察到什么，再选择能够完整证明该结果的最低强度，并写清：

```text
层级名称与触发条件：
该层级必须覆盖的对象和状态：
需要的证据与资源：
必须执行的步骤：
通过标准和允许保留的差异：
升级到更高层级的条件：
```

较低层级可以减少证据粒度、覆盖面或验收深度，同时保留使该层级成立的完整步骤。用户明确要求，或高代价错误、外部写入、复杂产物等可说明风险需要时进入较高层级；来源项目的高保真流程保持在对应高强度分支。

## 6. 写清触发边界

必须回答：

- 用户通常会怎么问？
- 哪些请求应该触发？
- 哪些相近请求不应该触发？
- 用户只点名 Skill 或只附加文件时，默认解释成什么意图？
- 触发后交付什么用户结果？

`description` 写真实触发场景和关键排除项，不写营销介绍，也不把所有深入能力都暗示为默认动作。

新建 Skill 的名称使用小写字母、数字和连字符，长度不超过 64 个字符，目录名与 frontmatter 的 `name` 完全一致。优先使用简短、以动作或稳定角色为中心的名称；只有工具名称确实能改善路由时才加命名空间。

## 7. 先展示示范输出骨架

在用户批准修改前，用代表性真实请求展示：

```text
第一步会做什么：
会读取或调用什么：
回答第一段会说什么：
正文包含哪些部分：
明确不会做什么：
在哪里停止：
```

这里只需展示足以确认方向的骨架，不提前完成整个任务。用户确认的是未来行为，不是文件名和目录结构。

## 8. 决定规则放在哪里

写入规则前读取 `references/instruction-hygiene.md`，完成限制性指令的四级分级。正向合同承担默认行为；条件边界承担权限、适用范围和方法强度选择；通过保留门槛的硬禁止在实际决策点出现一次。

`SKILL.md` 只保留会改变默认行为的内容：

- 负责什么和不负责什么；
- 信息与操作边界；
- 第一判断和主流程；
- 默认路径与按需分支；
- 默认输出和停止条件；
- 必须执行的质量标准；
- reference 与 script 的读取或运行条件。

过长模板、详细清单、schema、领域知识和边界明确的专业能力才放 `references/`。失败样本、回归案例、纠正记录、案例提示词、案例输出和案例衍生的默认方案不放入任何活动目录。每个 reference 必须由 `SKILL.md` 写清：

```text
什么时候读：
路径：
读它改变什么动作：
```

重复、确定、手写容易错的解析、转换、校验、排序或批处理写进 `scripts/`。`SKILL.md` 写清输入、输出、触发条件和异常处理。自然语言请求、输出和运行工作区只在当前任务或项目自身的受控日志中存在。

最终产物会直接使用的模板、图片、字体、风格档案、schema、starter project 等内容放入 `assets/`。来源资产在目标 Skill 生产链路中有明确消费者时随能力迁移；价值所需资产保持原职责，其余文件留在来源项目。

根据任务的可变程度决定约束强度：存在多种合理方法时写判断原则；有稳定模式但允许参数变化时使用伪代码或带参数脚本；步骤脆弱、重复且结果必须一致时使用少量明确参数的脚本。确定性操作进入脚本，现场判断保留选择原则。

采用渐进加载并保持第一判断的唯一真源：frontmatter 只写 `name` 和 `description`；`SKILL.md` 保留默认流程与资源路由，尽量控制在 500 行以内；过重细节放进由 `SKILL.md` 直接指向的一层 reference。资源路由保持一层，每项行为规则保留一个活动位置。

Skill 活动目录只保留执行所需内容，不创建 README、安装指南、更新日志、快速参考或过程说明。脚本必须实际运行；模板与资产按下面的资源验证等级检查。只创建已有真实内容的资源目录，不保留空目录和占位资源。

### 资源验证等级

资源验证以当前任务真实存在的生产者和消费者为准，不为提高等级制造演示项目或自然语言案例。

1. **结构可达**：`SKILL.md` 写清触发条件和路径，资源存在，输入、输出、必填字段、失败处理和目标消费者明确。只创建或改造 Skill、当前没有真实下游任务时，至少达到此级，并明确尚未发生真实实例化。
2. **真实实例化**：当前用户请求本来就会产生该资源时，使用本次真实输入生成或填写它，再由约定的下一步读取。正式生产者输出作为消费者输入。适用于模板、schema、配置或中间规格已经进入当前交付链路的任务。
3. **端到端消费**：用户同时要求实施，或外部写入、复杂产物和高代价错误使真实验收必要时，从正式生产者经过文件、配置或存储边界到正式消费者，并检查用户可观察结果。核心环节使用真实实现，正式输出贯穿验证链路。

当前任务不具备下一等级的真实前提时，在已经证明的等级停止并报告缺口。这不是验证失败；把结构可达说成已经实际使用，或者为了满足检查而虚构消费者，才是失败。

### 新建目录的固定顺序

1. 确认行为合同和 Skill 名称。用户指定目标父目录时使用该位置；未指定时使用 `$HOME/.agents/skills`，并在写入前明确告知实际路径。
2. 根据最终定位生成 `display_name`、`short_description` 和包含 `$skill-name` 的 `default_prompt`，字段细节使用主流程已经加载的 UI 元数据规则。
3. 运行 `scripts/init_skill.py`，传入名称、父目录、description 和三项 UI 文案。目标目录已经存在时停止，不覆盖。
4. 用已确认的正向流程替换初始化正文中的全部待填写内容；只有真实内容就绪时才创建资源文件和目录。
5. 新增脚本要实际执行；新增模板或资产按当前任务可达到的资源验证等级检查，不创建假消费者。
6. 正文完成后运行 `scripts/generate_openai_yaml.py`，从最终 Skill 定位重新生成 UI 元数据。
7. 运行 `scripts/quick_validate.py`，再重新读取 `SKILL.md` 和 `agents/openai.yaml`，确认最终文件而不只确认命令返回成功。

## 9. 写成可执行的人话

- 默认使用目标用户能理解并能据此行动的语言。
- 第一句先回答问题，不先解释研究过程。
- 来源中的专业术语、实现动词、产品分类和宣传说法先作为证据理解，再按当前用户的任务决定是否进入交付。事实得到核实只说明它可以使用；只有会改变理解、判断或行动的信息才占用最终篇幅。
- 内部合同字段、schema、路由名、检查标签和过程记录服务 Agent 协作。到达用户可见输出前，把它们写成具体的人、动作、条件、可观察变化和结果。用户明确询问实现、协议或数据结构时，再展示相应内部结构。
- 专业词对当前任务确有必要时保留精确名称，并在第一次出现时用当前情境说明它指向什么对象、动作或后果。语义转换以实际含义和用户结果为单位，不靠替换几个近义词完成。
- 模板写信息职责、选择条件、固定格式、可变位置和通过标准。只复述一次任务答案的完整成句、专用措辞和来源项目特有的表达留在当前任务；协议、稳定标准或用户明确要求逐字保留的文字继续作为构成性内容。案例库仍可提供完整案例，用于学习结构、节奏和表达机制。
- 数量、分类、目录、术语和证据标签用于辅助具体说明。
- 用动作和条件写规则，不用“清楚、准确、专业、深入”这类无法执行的要求。
- 每句话必须改变下一步判断、动作、输出或验收；否则删除。
- 限制性语句逐项通过约束清洗。一般能力提醒和抽象品质要求退出提示词，有效目标转成来源、动作、产物与验收，少数硬禁止保留具体触发范围与实质后果。

交付前把内部工作包移开，再单独阅读最终输出：目标用户能否直接知道发生了什么、与自己有什么关系、能做什么；内部字段和过程名是否仍在替用户说话；每个保留术语是否真的承担当前任务所需的精度。这里检查语义和读者结果，不建立禁词表，也不触发自动返修。

## 10. 临时核对跨表层行为

交付前在当前任务中临时核对至少两个表层内容明显不同的正常请求：

1. 代表性请求：包含用户实际附件、上下文和限制。
2. 迁移请求：更换人物、对象、动作、场景、措辞和数值，检查同一判断机制能否产生随输入变化的合适结果。

临时检查第一步、允许来源、允许动作、输出开头、停止条件和用户可观察结果。会生成用户可见内容时，同时检查来源语言、内部工作语言和最终用户语言已经分开。两个请求使用表层明显不同的对象与场景，并产生各自具体答案。

能力存在强度层级时，临时核对还要证明普通请求不会自动采用最高强度，并检查明确升级后的证据、动作和验收确实随层级变化。

吸收边界明确的专业能力时，两个正常请求都应属于该能力的适用范围，用来证明构成性结构能够跨内容复用；再临时核对一个相邻但不适用的正常请求，证明目标 Skill 会保留原默认路径而不误套该能力。最后比较修改前后，确认目标 Skill 确实新增或强化了用户可观察的结果，而不是只增加通用措辞。

请求原文、提示词、输出、检查报告、fixture 和工作区都不写入 Skill。需要检查自然路由或高代价动作边界时，也只在当前任务中临时判断，不建立负控、回归文件或自然语言 Harness。

普通验收直接核对规则能否处理两个请求，并在交付时准确说明这是临时推演还是实际运行。重新加载 Skill、CLI、子 Agent、新进程、完整项目扫描和被测项目运行留给明确要求或高代价风险触发的独立验证；结构校验与行为核对分别报告。

新建 Skill 是例外：初始化器、元数据生成器和校验器属于正在交付的核心链路，必须在临时隔离目录中实际运行一次，并由后续读取证明文件确实生成、最终正文能被校验器读取、UI 元数据能被产品侧字段消费者解析。临时目录和运行输出不迁入 Skill；清理临时目录需要遵守当前环境的删除授权。

只有用户明确要求独立验收，或 Skill 涉及外部写入、复杂可复用产物、高代价错误，或最终结果无法在当前任务可靠观察时，才升级验证。启动额外进程前先取得用户同意，并使用临时隔离位置；结束后不把自然语言输入、输出或工作区迁入 Skill。

## 11. 返回结果

返回时只说：

- 改了哪些关键文件；
- 默认行为与按需行为怎样变化；
- 哪两个表层不同的正常请求完成了临时核对；
- 新增限定能力时，相邻不适用请求的边界核对以及目标 Skill 的可观察能力变化；
- 哪些只做了结构检查，以及为什么。
