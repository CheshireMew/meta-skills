# Skill 设计与行为合同

用于新建、重写、更新或审计一个 Skill。目标不是把文件写完整，而是让真实调用产生用户认可的结果。

设计顺序固定为：先写独立成立的正面流程，再写必要边界；先把问题阻止在最早判断点，再考虑检测。历史案例不能定义默认行为，也不能作为 Skill 资产保存。

## 1. 先判断要不要做成 Skill

- 这件事是否会重复发生？
- 用户是否反复解释相同标准？
- 少一个判断是否容易跑偏？
- 它缺的是流程、判断标准、模板、脚本还是资料路径？
- 如果只是一次性回答，不创建 Skill。

## 2. 从真实请求还原用户本意

先保留用户原话，不先改写成领域术语。分别写出：

- 用户真正想拿到的结果。
- 用户明确给了哪些材料。
- 用户明确允许或禁止哪些动作。
- 哪些只是设计者认为“更专业、更完整”，但用户没有要求。

优先级固定为：

```text
用户明确结果和边界
→ 默认行为
→ 完成任务所需的方法
→ 领域最佳实践
→ 可选的完整性增强
```

后面的内容不能扩大前面的默认范围。仓库级质量原则约束“怎样做好”，不能自动变成用户必须看到的额外交付。

## 3. 判断职能是否过窄或过宽

当前一句请求通常只能说明这次要做什么，不一定完整定义 Skill 长期负责什么。创建或优化 Skill 时，查看当前可用的对话、用户提供的历史材料、目标 Skill 的现有定位和真实使用方式，提取反复出现的最终结果、相邻能力、继续追问、明确接受、明确排除和误触发。

证据强度按以下顺序判断：

1. 用户明确说明期望的上层角色、最终结果或排除边界；
2. 用户反复提出相邻任务、重复选择同一方法，或在后续任务中自然依赖此前能力；
3. 结果经过可观察验收，或者存在当前产品、团队规则与独立方法依据；
4. 单次成功、未修改、未回复和没有反对只能提出假设，不能独立决定长期职能。

把相邻能力按共同用户结果归并。多项能力共同构成一个稳定专业角色时，建议扩大到这个上层职能，不要求用户逐项列举；彼此没有共同结果、会改变完全不同的第一判断或需要不同权限时，保持分支或拆成其它 Skill，不堆成功能合集。

建议缩小时，需要明确排除、持续误触发、与目标角色稳定冲突、职责被其它 Skill 接管或用户已经确认角色收敛。历史中没有出现某项能力只说明证据不足，不能单独证明应当删除。

每次范围判断写清：

```text
当前 Skill 实际职能：
历史反映的用户最终结果：
相邻能力为什么属于或不属于同一上层角色：
建议保持、扩大或缩小：
默认能力与按需能力：
明确排除：
信息来源与操作权限是否变化：
证据强度、假设与需要确认的关键分歧：
```

职能范围回答“能处理什么”，动作边界回答“默认可以做什么”。扩大职能不能顺带取得联网、运行、写入、发送、发布或删除权限。证据足够时把完整定位作为一个行为合同让用户确认；只有关键分歧会改变 Skill 身份、默认来源、操作权限或主要交付时才逐项追问。

## 4. 写行为合同

创建文件计划前，完成以下合同：

```text
代表性真实请求：尽量使用用户这次的原话、附件和上下文
用户最终想得到什么：能从用户视角观察到的结果
当前职能与建议职能：保持、扩大或缩小，以及证据
当前结果最有价值的能力与仍然缺少的能力：用户现在能稳定得到什么、哪类请求仍然做不到或做不稳
来源价值与最小完整能力单元：哪些判断、知识、结构、脚本、模板或资产需要共同迁移
默认信息真源：本地文件、某个应用、某个仓库、用户输入或其它明确来源
默认允许读取什么：文件、页面、资源和 reference 范围
默认允许执行什么：只读检查、联网、运行、安装、写入、发送或其它动作
最早可预防问题的判断点：在什么动作发生前必须确定什么
默认正向流程：用户不需要提醒时也会主动执行的正确步骤
第一步必须做什么：收到请求后的首个判断或动作
默认输出：第一段回答什么，后续按什么顺序展开
按需分支：只有用户说出哪些意图时才能进入
停止条件：做到什么立即交付，不再继续研究或扩张
正向通过标准：用户不需要先遭遇错误或提出纠正就能观察到什么
```

通过标准：另一个 Agent 只看这份合同，就能判断一次真实运行有没有偏离用户本意。

行为合同中的“默认”是用户没有补充说明时的稳定工作流程，不是设计者替具体内容预选答案。人物、对象、动作、场景、风格、措辞和数值不能因为出现在一次案例中就升级为全局默认；它们如果是某项边界明确的专业能力成立所需的构成性结构，可以保留在该按需分支、reference、script 或 asset 中，并写清选择条件与可调参数。

## 5. 找出会改变方法的分支

只有会改变第一步、来源、动作、输出或停止条件的差异才建立分支，例如：

- 本地文件与远程 URL；
- 快速解释与实际运行验证；
- 可运行程序与提示词、模板、配置合集；
- 只读分析与允许写入；
- 默认回答与用户明确要求的详细报告。

不要为文件后缀、平台名称或次要差异建立无行为变化的分支。默认路径必须独立完整，深入分支不能反向污染默认路径。

### 能力存在强度层级时

来源方法或目标结果存在不同精度、覆盖、成本、时效或风险等级时，不把最严格流程直接设为统一默认。先确定用户需要观察到什么，再选择能够完整证明该结果的最低强度，并写清：

```text
层级名称与触发条件：
该层级必须覆盖的对象和状态：
需要的证据与资源：
必须执行的步骤：
通过标准和允许保留的差异：
升级到更高层级的条件：
```

较低层级可以减少证据粒度、覆盖面或验收深度，但不能删掉使该层级自身无法成立的步骤。较高层级只能由用户明确要求，或由高代价错误、外部写入、复杂产物等可说明的风险触发；不能因为来源项目默认高保真、高强度或全覆盖，就让目标 Skill 的普通请求承担相同成本。

## 6. 写清触发边界

必须回答：

- 用户通常会怎么问？
- 哪些请求应该触发？
- 哪些相近请求不应该触发？
- 用户只点名 Skill 或只附加文件时，默认解释成什么意图？
- 触发后交付什么用户结果？

`description` 写真实触发场景和关键排除项，不写营销介绍，也不把所有深入能力都暗示为默认动作。

新建 Skill 的名称使用小写字母、数字和连字符，长度不超过 64 个字符，目录名与 frontmatter 的 `name` 完全一致。优先使用简短、以动作或稳定角色为中心的名称；只有工具名称确实能改善路由时才加命名空间。

## 7. 先展示示范输出骨架

在用户批准修改前，用代表性真实请求展示：

```text
第一步会做什么：
会读取或调用什么：
回答第一段会说什么：
正文包含哪些部分：
明确不会做什么：
在哪里停止：
```

这里只需展示足以确认方向的骨架，不提前完成整个任务。用户确认的是未来行为，不是文件名和目录结构。

## 8. 决定规则放在哪里

`SKILL.md` 只保留会改变默认行为的内容：

- 负责什么和不负责什么；
- 信息与操作边界；
- 第一判断和主流程；
- 默认路径与按需分支；
- 默认输出和停止条件；
- 必须执行的质量标准；
- reference 与 script 的读取或运行条件。

过长模板、详细清单、schema、领域知识和边界明确的专业能力才放 `references/`。失败样本、回归案例、纠正记录、案例提示词、案例输出和案例衍生的默认方案不放入任何活动目录。每个 reference 必须由 `SKILL.md` 写清：

```text
什么时候读：
路径：
读它改变什么动作：
```

重复、确定、手写容易错的解析、转换、校验、排序或批处理才写进 `scripts/`。`SKILL.md` 必须写清输入、输出、触发条件和异常处理。脚本不得收集或长期保存自然语言请求、输出和运行工作区。

只有最终产物会直接使用的模板、图片、字体、风格档案、schema、starter project 等内容才放 `assets/`。来源项目的资产只有在目标 Skill 的生产链路中有明确消费者时才迁移；不能把价值所需资产抽象成文字后丢弃，也不能为了“完整”复制没有消费者的文件。

根据任务的可变程度决定约束强度：存在多种合理方法时写判断原则；有稳定模式但允许参数变化时使用伪代码或带参数脚本；步骤脆弱、重复且结果必须一致时使用少量明确参数的脚本。不能用大段说明替代本可确定执行的操作，也不能把需要现场判断的工作强行锁成固定答案。

采用渐进加载，但保持第一判断的唯一真源：frontmatter 只写 `name` 和 `description`；`SKILL.md` 保留默认流程与资源路由，尽量控制在 500 行以内；过重细节放进由 `SKILL.md` 直接指向的一层 reference。不要让 reference 继续深层路由，也不要在 `SKILL.md` 和 reference 重复同一规则。

Skill 活动目录只保留执行所需内容，不创建 README、安装指南、更新日志、快速参考或过程说明。脚本必须实际运行；模板与资产按下面的资源验证等级检查。只创建已有真实内容的资源目录，不保留空目录和占位资源。

### 资源验证等级

资源验证以当前任务真实存在的生产者和消费者为准，不为提高等级制造演示项目或自然语言案例。

1. **结构可达**：`SKILL.md` 写清触发条件和路径，资源存在，输入、输出、必填字段、失败处理和目标消费者明确。只创建或改造 Skill、当前没有真实下游任务时，至少达到此级，并明确尚未发生真实实例化。
2. **真实实例化**：当前用户请求本来就会产生该资源时，使用本次真实输入生成或填写它，再由约定的下一步读取；不能用消费端手写结果代替生产者输出。适用于模板、schema、配置或中间规格已经进入当前交付链路的任务。
3. **端到端消费**：用户同时要求实施，或外部写入、复杂产物和高代价错误使真实验收必要时，从正式生产者经过文件、配置或存储边界到正式消费者，并检查用户可观察结果。核心环节不能被 mock，测试夹具不能冒充正式输出。

当前任务不具备下一等级的真实前提时，在已经证明的等级停止并报告缺口。这不是验证失败；把结构可达说成已经实际使用，或者为了满足检查而虚构消费者，才是失败。

### 新建目录的固定顺序

1. 确认行为合同和 Skill 名称。用户指定目标父目录时使用该位置；未指定时使用 `$HOME/.agents/skills`，并在写入前明确告知实际路径。
2. 根据最终定位生成 `display_name`、`short_description` 和包含 `$skill-name` 的 `default_prompt`，字段细节使用主流程已经加载的 UI 元数据规则。
3. 运行 `scripts/init_skill.py`，传入名称、父目录、description 和三项 UI 文案。目标目录已经存在时停止，不覆盖。
4. 用已确认的正向流程替换初始化正文中的全部待填写内容；只有真实内容就绪时才创建资源文件和目录。
5. 新增脚本要实际执行；新增模板或资产按当前任务可达到的资源验证等级检查，不创建假消费者。
6. 正文完成后运行 `scripts/generate_openai_yaml.py`，从最终 Skill 定位重新生成 UI 元数据。
7. 运行 `scripts/quick_validate.py`，再重新读取 `SKILL.md` 和 `agents/openai.yaml`，确认最终文件而不只确认命令返回成功。

## 9. 写成可执行的人话

- 默认使用用户能理解的语言。
- 第一句先回答问题，不先解释研究过程。
- 第一次出现术语时，用“谁做什么、得到什么”解释。
- 数量、分类、术语和证据标签只能辅助说明，不能代替内容。
- 用动作和条件写规则，不用“清楚、准确、专业、深入”这类无法执行的要求。
- 每句话必须改变下一步判断、动作、输出或验收；否则删除。

## 10. 临时核对跨表层行为

交付前在当前任务中临时核对至少两个表层内容明显不同的正常请求：

1. 代表性请求：包含用户实际附件、上下文和限制。
2. 迁移请求：更换人物、对象、动作、场景、措辞和数值，检查同一判断机制能否产生随输入变化的合适结果。

临时检查第一步、允许来源、允许动作、输出开头、停止条件和用户可观察结果。两个请求不能只替换同义词，也不能被同一个具体答案满足。

能力存在强度层级时，临时核对还要证明普通请求不会自动采用最高强度，并检查明确升级后的证据、动作和验收确实随层级变化。

吸收边界明确的专业能力时，两个正常请求都应属于该能力的适用范围，用来证明构成性结构能够跨内容复用；再临时核对一个相邻但不适用的正常请求，证明目标 Skill 会保留原默认路径而不误套该能力。最后比较修改前后，确认目标 Skill 确实新增或强化了用户可观察的结果，而不是只增加通用措辞。

请求原文、提示词、输出、检查报告、fixture 和工作区都不写入 Skill。需要检查自然路由或高代价动作边界时，也只在当前任务中临时判断，不建立负控、回归文件或自然语言 Harness。

普通验收不要求重新加载 Skill，也不启动 CLI、子 Agent、新进程、完整项目扫描或被测项目运行。直接核对规则能否处理两个请求，并在交付时准确说明这是临时推演还是实际运行；结构校验通过仍不能代替这一步。

新建 Skill 是例外：初始化器、元数据生成器和校验器属于正在交付的核心链路，必须在临时隔离目录中实际运行一次，并由后续读取证明文件确实生成、最终正文能被校验器读取、UI 元数据能被产品侧字段消费者解析。临时目录和运行输出不迁入 Skill；清理临时目录需要遵守当前环境的删除授权。

只有用户明确要求独立验收，或 Skill 涉及外部写入、复杂可复用产物、高代价错误，或最终结果无法在当前任务可靠观察时，才升级验证。启动额外进程前先取得用户同意，并使用临时隔离位置；结束后不把自然语言输入、输出或工作区迁入 Skill。

## 11. 返回结果

返回时只说：

- 改了哪些关键文件；
- 默认行为与按需行为怎样变化；
- 哪两个表层不同的正常请求完成了临时核对；
- 新增限定能力时，相邻不适用请求的边界核对以及目标 Skill 的可观察能力变化；
- 哪些只做了结构检查，以及为什么。
