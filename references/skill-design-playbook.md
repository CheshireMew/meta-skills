# 设计或重做一个 Skill

用于新建 Skill、重做整体职能，或者一次改造会影响多个主要能力时。目标是让真实请求稳定得到用户需要的结果，不是把目录和字段填满。

## 1. 先判断是否值得做成 Skill

适合做成 Skill 的事情通常会重复发生，用户会反复解释相同标准，或者少一个关键判断就容易走偏。只需要一次回答、没有长期做法可复用时，直接完成任务，不创建 Skill。

新建前把用户想得到的结果写成一个自然搜索词，运行：

```text
npx skills find "<query>"
```

第一轮没有实质结果时，最多换一个自然同义词。只阅读真正相关候选的活动 `SKILL.md`，然后说明它能否直接满足、只能提供部分参考，还是仍需新建。安装量只能说明关注度，不能代替质量判断；不自动安装，也不因找到相似方案就取消用户明确要求的创建任务。

## 2. 从用户原话确定 Skill 要负责什么

先写清：用户真正想拿到什么，提供了什么材料，允许或拒绝哪些动作，哪些只是设计者觉得“更完整”但用户没有要求。

确定长期职能时，优先看用户明确说明的角色和结果，其次看反复出现的相邻请求、重复选择的做法和真实使用结果。一次成功、一次沉默或“业内通常这样做”只能提出猜想，不能直接扩大默认职能。

多项请求如果共同服务一个稳定结果、共享主要材料和专业判断，可以归在同一 Skill。只有用户目标、权限、外部风险或必要专业方法长期不同，才考虑拆成不同 Skill；来源、成品形式或内部步骤不同，本身不要求分流。

## 3. 改现有 Skill 前盘清用户结果

查看主文件及它直接选择的参考说明、脚本、模板、示例、素材和真实使用入口。临时记录：

- 什么请求会使用这项能力或资源；
- 用户最终得到什么；
- 哪些内容和工具确实参与；
- 本次哪些用户结果继续保留，哪些需要修复或退出。

能力以 Skill 能完成的一类真实请求，以及会实质改变结果的必要材料、工具和权限为准。文件、字段、路径名、步骤、默认包装和检查形式只是实现；更简单的做法能产生同样结果时，可以直接替换。

用户没有提到某项真实能力，不构成退出依据；当前搜索不到使用位置时先检查是否曾被旧改造切断。保留结果由新做法接通后，被替代的旧实现应当退出，不保留兼容层。

## 4. 写一份短而完整的未来行为说明

用代表性真实请求说明：

```text
用户会怎样提出请求：
最终要得到什么：
需要哪些材料和工具：
默认怎样完成：
用户会看到什么：
```

只有程序必须读取固定产物时，再补字段、格式、生成和读取方式。只有外部写入或高风险动作时，再补权限、准确目标和恢复办法。确实存在不能同时成立的结果或不同机器协议时，直接说明差异；没有时不为了完整补条件。

这份说明离开反面清单后，也应当让另一个执行者知道怎样完成正常请求。没有改变实际做法的字段就是噪声。

目标 Skill 需要使用本机程序、私人资料库、账户或会随机器变化的路径时，只确认这些前提由哪里提供、缺少时哪项能力停止；详细配置留给运行资源方法，不能让本机路径扩张成所有 Skill 的默认设施。

## 5. 让默认工作直接成立

把默认材料、共同要求和正常动作直接写在一起。来源、成品形式、处理深度和表达选择通常可以同时交给模型判断，不需要先变成任务分类或选择节点。

只有用户结果确实不能同时成立、权限不同、存在不可逆外部影响，或者程序必须遵守不同固定协议时，才分别说明做法。深入研究和高成本工具只在结果确实需要时使用，但不把模型可以自然完成的判断写成硬路由。

`SKILL.md` 说明正常工作和何时读取专业资源；参考说明、脚本和素材只提供各自内容，不覆盖用户结果。多个创作参考可以一起进入上下文，不要求主文件预先选定主次、数量或采用方式。

多阶段工作只需按真实依赖排序：材料和授权先于使用，产生结果的步骤先于读取结果的步骤，必须看到成品才能做的检查放在成品之后，检查失败回到真正产生问题的步骤。不要把一种常见顺序写成所有任务都必须遵守的固定流程。

## 6. 把内容放到真正会使用它的位置

`SKILL.md` 保留触发边界、正常工作、用户权限、必要材料和资源读取说明。过长方法、领域知识和完整示例放到确实会被读取的参考说明或素材中。

自然语言能稳定表达的判断留在说明里。只有重复、确定、手写容易错而且结果必须一致的解析、转换、排序或检查才写成脚本。只有程序必须解析固定字段时才建立固定数据格式。

完整示例、模板、脚本和素材在正常请求确实会读取时可以长期保留。失败样本、纠正故事、临时提示词、临时回答和本次比较记录不进入活动目录。

主文件必须同时不超过 220 行和 14,000 个字符。超出时先合并重复规则、删除内部解释，再把确实必要的详细方法移到参考说明；不能提高上限、拆行规避，也不能为了变短删除用户能力。

## 7. 写入前确认具体方案

用户只要求审查或解释时保持只读。准备创建、修改、移动、归档或删除 Skill 活动文件时，第一次写入前展示一份短而完整的方案：用户以后会得到什么，哪些结果和必要材料继续保留，哪个旧实现会被替换，准备变动的文件，以及怎样用真实结果确认完成。没有真正例外时不补写条件和分支。展示后停止，等待用户明确确认。

最初的创建、改造、优化或修复请求只说明目标，不等于批准尚未展示的方案。用户明确要求跳过确认并立即实施，或者看过方案后明确批准时，才进入实现。方案外如果还要改变用户结果、动作权限、必要材料或确认边界，必须补充说明并再次取得同意。内部实现的简化由已确认方案承担，不逐项恢复旧步骤。

目标已经有 Git 仓库，并且已经配置要推送到哪个 GitHub 仓库和分支时，用户批准具体方案也包含把本轮准确改动提交并推送到当前跟踪分支，再核对远端最新提交，不再单独询问相同的发布授权。用户选择只改本地时停在本地。创建远端、改变可见性、强制推送、删除、改变未经确认的分支和夹带其它修改仍需单独授权。

## 8. 新建 Skill 的顺序

1. 在写入方案中说明 Skill 名称、未来行为和目标父目录。名称使用小写字母、数字和连字符，不超过 64 个字符，目录名与 `name` 一致。用户没有指定位置且当前环境没有另行规定时，使用 `$HOME/.agents/skills`，并用当前系统的实际路径说明；当前环境已经提供其它个人 Skill 根目录时，以那个位置为准。
2. 用户确认方案后，准备列表中显示的名称、25–64 字符简述和一条包含 `$skill-name` 的正常示范请求。
3. 运行 `scripts/init_skill.py` 建立最小入口。目标目录已存在时停止，不覆盖。
4. 用最终行为替换占位内容，只在真实材料就绪时创建参考说明、脚本或素材。
5. 运行 `scripts/generate_openai_yaml.py` 生成界面信息。
6. 运行 `scripts/quick_validate.py`，再重新读取最终 `SKILL.md` 和 `agents/openai.yaml`。

## 9. 迁移能力时判断实际完成到哪里

迁移对象是用户能得到的完整能力，不是旧文件结构。先还原来源怎样使用真实规则、材料、配置和工具产生结果，再确定目标怎样用最简单的完整做法承接；不要求保留来源的路径名、步骤数和固定包装。

完成程度分三层，用人话如实报告：

1. **入口已经接好**：目标写清触发条件和使用位置，所需文件存在，但还没有真实材料或下游任务证明实际使用。
2. **真实材料已经读到**：正式入口能够读取本次真实配置、案例、数据或账户，下一步也收到它，但还没有形成最终用户结果。
3. **用户结果已经产生**：代表性请求从目标入口出发，使用真实材料经过正式步骤，用户最终能看到或使用结果。

不能用临时样本、消费端手写数据或假使用者把前两层说成第三层。缺少下一层所需的真实条件时，停在已经证明的位置并说明缺什么。

## 10. 按结果核对并交付

结构检查只证明文件和固定格式。文字和普通 Skill 修改用新的正常请求审读理解、材料使用和最终结果；创作看实际成品；研究看来源与推断；程序读取的产物用同一份真实输出走完生成和使用；高风险动作核对权限和外部结果。

最后先说新的行为怎样工作和用户怎样使用，再说明关键文件与实际核对。已经配置要推送到哪个 GitHub 仓库和分支，而且用户没有选择只改本地时，完成精确提交、推送和远端核对后再报告发布状态。达到用户要求后停止。
