# 资料提炼清单

用于从压缩包、仓库、旧项目、外部方法论、示例 Skill 或大量文档中提炼目标 Skill 值得获得的完整能力，而不只收集能够跨领域复述的通用规则。

## 1. 先确定提炼目标，再分材料

调用本文件前，主流程应已写清目标 Skill 的行为合同、当前价值与能力缺口。材料只用于寻找价值因果链，不能替代用户定义默认结果。

候选信息如果不会改变触发边界、执行步骤、方法选择、可交付能力、验收标准或实际风险，直接跳过，不因为它可以考据就继续研究。

来源项目中的“完整做法”不能自动变成目标 Skill 的默认流程。先找出它让用户得到什么结果，再追踪哪些判断、知识、步骤、约束、脚本、模板和资产共同产生该结果；只有目标 Skill 需要这项价值时，才把最小完整能力单元迁入默认路径或边界明确的按需分支。

按优先级看：

1. 原始 `SKILL.md`、脚本、模板和稳定规范。
2. README、设计文档、方法说明。
3. 多个相互独立来源中反复出现的结构。
4. 完整项目中能互相印证的规则、实现、资源与原始产物；它们可以证明限定能力存在，但不能单独建立全局默认。
5. 孤立示例、单段提示词或一次输出只用于提出待判断的问题。
6. 宣传、安装和与执行无关的品牌表达通常不吸收。

## 2. 先找主流程

- 这个项目到底让 agent 做什么？
- 用户通常怎么触发？
- 输入是什么？
- 输出是什么？
- 中间必须经过哪些步骤？
- 哪些步骤不能跳？
- 它默认读取哪些来源、执行哪些动作？
- 它在什么条件下停止？

## 3. 再找价值因果链与能力单元

是否值得吸收、应成为默认还是限定能力，以及职能是否变化，由主流程的价值门槛决定。本文件只负责从外部材料中证明能力由什么组成。先把候选内容分成三层：

- **用户价值**：这套材料让谁完成了什么、得到什么目标 Skill 当前无法稳定提供的结果。
- **操作结构**：输入字段、信息顺序、处理步骤、输出骨架和检查位置。
- **实现载体**：哪些专业知识、约束、脚本、模板、schema 和资产让操作结构能够稳定产生该结果。

抽象时不能顺手丢掉确实会改变执行或决定结果特质的操作结构与实现载体；保留具体结构时也不能把原项目的案例内容包装成通用模板。判断、结构和资源共同产生价值时必须作为一个能力单元迁移，不能只留一句原则、让关键资源失去消费者。

不要按“人物、对象、动作、场景、风格、措辞和数值”直接整类删除。先逐项判断：

- **偶然细节**：替换后不影响能力，只属于当前请求或展示样本。
- **可调参数**：具体值随输入变化，但参数维度和选择方法必须保留。
- **构成性细节**：删除后能力身份、结果质量或可复现性明显受损，必须保留在限定能力中。

外部材料还要证明因果关系，而不只是共同出现：规则说明为什么做，实现说明怎样做，资源与原始产物说明该机制确实进入结果。证据只覆盖其中一层时，把缺口保留为假设，不用完整项目的外观替代机制证据。

来源存在多个强度层级时，分别提取每个层级增加了什么证据、动作、资源、成本和通过标准。目标 Skill 可以只迁移其中一层或保留可调分级，但不能把最高层级的全部流程伪装成所有请求都必须执行的构成性结构。

外部材料中发现 script、模板、schema、starter project 或资产时，记录它的生产者、输入、输出、消费者、失败处理和在价值因果链中的职责。只有职责不可被目标 Skill 的现有资源等效承担时才迁移；验证等级使用主流程已经加载的设计规则。

## 4. 决定写入位置

写入位置和资源验证等级使用主流程已经加载的设计规则。本文件只增加一个来源约束：来源资源必须能说明自己在能力链中的职责；没有消费者、已被目标资源等效替代或只用于展示原项目的文件不迁移。

## 5. 保留哪些细节

保留会改变能力选择、执行或结果的细节：

- 触发条件。
- 操作顺序。
- 必填字段。
- 例外边界。
- 通过标准。
- 停止条件。
- 失败时怎么降级。
- 专业结果成立所需的参数范围、结构、工具、模板和资产。
- 让限定能力与其它方法可观察地区分开的构成性细节。

删掉：

- 与能力成立无关的专属人物、平台包装和项目事实。
- 与执行无关的命名史、发明史、人物评价和传播轶事。
- 装饰性案例。
- 失败样本、回归案例、纠正故事、案例提示词和输出。
- 只绑定一次请求、替换后不影响能力的固定动作、场景、风格、措辞和数值。
- 宣传语。
- 通用教程。
- 没有消费者、无法验收或只复述原案例的模板。

## 6. 提炼后的检查

- 是否只检查了会改变目标 Skill 行为、产物、风险或成本的材料？
- 规则、实现、资源和原始产物是否共同证明能力，而不是只看到名称或宣传？
- 偶然包装是否被删除，构成性结构、可调参数和强度层级是否被保留？
- 如果不看来源也会得到相同结论，是否继续寻找专业判断、操作结构或实现载体？
- script、模板、schema 和资产是否有明确职责与消费者，并按实际达到的等级验证？
- 来源项目的完整流程是否没有反向扩大用户确认的默认范围？
- 是否没有把临时请求、输出、报告或工作区写回材料与 Skill？

## 7. 交付方式

最终交付格式以 `SKILL.md` 第 7 步为准；此外说明从哪些材料提炼、哪些实现资源被保留或舍弃及原因。结构校验、临时行为推演和真实消费验证必须分别标明。
