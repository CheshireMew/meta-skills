# 交付前的最终核对

只在新建、能力迁移、复杂长期资源、高风险动作、顽固问题独立验收或仓库发布前使用。普通文字和普通创作修改不加载本清单；只检查本次实际涉及的部分。

## 所有任务共同检查

- 第一段是否直接回答用户问题，所有说明是否使用目标用户能理解的语言；必要专业词是否在第一次出现时解释？
- 是否忠实保留用户原意、事实、关系、详略、主次、确定程度和材料作用，没有因通俗化或内部分类而改写需求？
- 用户列举的是完整范围还是共同问题的例子；修改是否覆盖了真正范围，没有机械限制在示例名称？
- 改造前仍然有效的用户能力、必要材料、权限和用户明确决定是否继续可用；当前路径、步骤、测试和固定包装是否没有被误当成用户决定？
- 涉及创建、修改、移动、归档或删除 Skill 活动文件时，是否已经先展示具体方案并等待明确确认；是否没有把最初提出目标误当成批准方案？
- 方案是否说明保持不变的用户结果和明确决定，以及真正改变的明确决定、退出实现、文件范围和核对方式；是否没有枚举无关步骤和测试制造确认负担？
- 新增、删除或改变系统选择、条件分支、路由、多候选、评审、二次细化、自动回退或多阶段处理，或者改变用户明确决定时，是否已经说明差异并取得同意？
- 从历史版本恢复能力时，是否只恢复获批内容，没有把同一版本中相邻的旧默认、旧目的、旧路由或旧资源分工带回来？
- 默认输入和共同要求是否直接加入工作；只有不同权限、不可逆外部动作或机器协议才被明确分开？
- 新增的字段、状态、流程、索引、脚本或检查器是否确实不可替代；简单方法足够时是否没有新增？
- 同义提醒、反面禁令、无人使用的记录、只证明过程的检查、旧入口和兼容做法是否已经收回？
- 当前没有入口的内容是否先检查了旧改造造成的断路，而不是直接判成无用？
- 失败输出、纠正故事、临时请求和工作区是否留在当前任务；正常工作需要的完整示例、模板和素材是否仍能被读取？
- 顽固问题的独立任务是否只收到用户原始请求或用户确认的交接、必要原始材料和可证明的代码版本，没有用父任务摘要替代用户要求，也没有继承诊断、旧输出、期望答案或验收标准？
- 是否任何时刻只有一个独立任务运行，并等它完整结束后才判断下一步？失败后是否先集中修改，而没有并行堆叠任务？
- `SKILL.md`、直接引用路径和 `agents/openai.yaml` 是否可读，`scripts/quick_validate.py <skill-folder>` 是否通过；是否明确说明这只证明结构？
- 保护用户结果和明确决定的测试是否继续成立；测试实现是否随获批结果正常迁移，没有反过来冻结旧步骤，也没有通过削弱测试掩盖语义变化？
- 主文件是否不超过 220 行和 14,000 个字符；如曾超出，是否先合并重复规则和删除内部解释，而不是提高上限或删除用户能力？
- Meta-skills 自身和目标 Skill 是否没有在同一轮同时改变后再互相证明有效；维护方法是否先完成并冻结？

## 创作与开放判断

- 是否给足真实材料、完整参考、用户硬要求和必要边界后，把角度、取舍、结构、篇幅、句子与结束位置交给模型，没有预写结构合同？
- 写前材料净化是否只删除不适合进入创作输入的内容，保留原文、顺序、来源边界和必要上下文，没有变成摘要、写作简报或正文骨架？
- 正常工作需要的多个完整案例、钩子或风格参考能否一起进入上下文；索引是否没有取代全文？
- 目标 Skill 已经规定为不同职责或互斥集合的案例、钩子和其它参考，是否仍保持独立，没有复用同一正文或被统一索引悄悄合并？
- 示例中的关键组织和表达方法是否与偶然的人物、数字、名称和段落数分开？
- 最终成品是否经过实际阅读、观看或试听；事实是否可靠，语言是否自然？
- 如果少量删改便能保留主体选材、事实关系和推进方式，是否只处理成品，没有据此增加写前决定？
- 研究和筛选过程是否只影响取舍，没有把检索分类、排除理由和内部标签自动写进成品？

## 能力载体选择

- 是否只在用户要求比较或尚未确定实现方式时选择载体，没有覆盖用户已经明确决定的提示词、Skill、CLI、软件或服务？
- 推荐是否从用户最终结果、实际使用频率、调用方式、精确性、状态、交互、账户、协作和持续运行需要出发，而不是默认把所有长期能力做成 Skill？
- 一次性工作是否直接完成；只需手动复用模型说明时是否交付提示词或模板；确定且必须一致的操作是否交给脚本或 CLI；需要状态、交互或成熟产品能力时是否优先使用现有软件、插件或服务？
- 创建前是否按实际载体检查真正相关的已有方案，并根据用户结果、材料、权限、环境和持续成本判断，而不是只搜索 Skill 或按知名度选择？
- 组合方案是否只有一个清楚的主结果，每个载体各自承担不可替代的职责，没有重复维护规则、数据、状态或入口？
- 最终是否给出可以直接使用或继续实施的结果；推荐非 Skill 方案时是否已经停止创建空壳 Skill？

## 概率性结果

- 结论是否来自多个代表性请求和重复采样，而不是一次成功或失败；是否保留了没有参与调试的请求？
- 比较是否固定了用户原始请求或确认交接、必要材料、完整参考、模型设置、代码版本和运行方式，并且只改变待验证因素？
- 是否分别观察了 `single@1`、`pass@N`、`critic@N` 和二次细化后的改善或退化，并同时考虑事实错误、延迟和成本？
- 候选覆盖、评审选择和二次细化的问题是否分开定位；是否没有因为生成不稳定就继续堆叠提示词？
- 多候选、评审或细化如果进入正式 Skill，是否有改善证据并已经取得用户对新路由的明确同意？
- 同一因果猜想连续两次受控核对仍不能解释结果时，是否已经停止据此修改并报告证据不足？
- 全新上下文是否只被用于检查对话隔离，没有被当作修改有效或根因成立的单独证据？

## 研究与分析

- 关键事实、时效和争议是否按结论风险核实；事实、推断和观点是否分得清？
- 目标 Skill 已经规定搜索用于发现信息、助推传播、核查事实或其它目的时，修改后是否仍保持原目的，没有静默改成另一种搜索？
- 来源是否真正支撑相应结论；没有影响用户理解和行动的检索过程是否留在内部？
- 直接引语、数字、日期、链接和明确归因是否保持准确；面向用户的解释是否自然？

## 程序必须读取的产物和长期资源

- 固定字段、格式、创建者、读取者和错误处理是否只有一套明确约定？
- 同一份真实产物是否从正式生成步骤进入正式读取步骤；是否没有用手写中间数据或假使用者代替？
- 需要锁定输入、哈希、版本、运行顺序或会话隔离时，是否由脚本或 CLI 承担，而不是继续扩写自然语言要求？
- 本机配置、私人库或外部工具是否真实存在并被正式入口读取；示例配置和临时目录是否没有冒充就绪？
- 正式机器资源是否有稳定名称、版本、唯一正文和公开入口，并能从新的外部项目读取？
- 普通文本参考是否没有被强加机器资源才需要的登记、版本和测试？
- 结构存在、真实材料被读取和最终用户结果是否分别如实报告？

## 能力迁移和外部材料

- 是否迁移了完整用户能力，而不只是相似文件；来源的真实材料、关键做法、使用位置和结果是否都已确认？
- 共同做法去掉来源专名、原句和偶然取值后，用两个表面明显不同但仍在目标范围内的对象代入，是否仍能自然产生同类结果？
- 必要差异是否继续保留为事实、边界或专业要求，没有被压成“按情况处理”，也没有被强行改造成普通请求的分流？
- 直接复用或改编的第三方内容是否追溯到准确的原始项目并按许可证致谢；独立实现是否没有虚构依赖？
- 保留项是否先接通新入口和实际使用位置；用户明确退出项是否没有被兼容或恢复逻辑带回？
- 入口已经接好、真实材料已经读到、用户结果已经产生是否没有混为一谈？

## 高风险和外部动作

- 权限、准确目标、影响范围和恢复办法是否在动作前确认？
- 发布、发送、删除、付费或不可逆写入后是否核对实际外部结果？
- 只有错误代价确实较高或用户明确要求时，是否才增加独立确认和更深检查？

## 仓库发布

- 目标已经配置要推送到哪个 GitHub 仓库和分支，而且用户没有选择只改本地时，是否只暂存本轮授权改动，提交并推送当前跟踪分支？
- 暂存差异是否没有夹带其它工作区修改，远端最新提交是否与本地提交一致？
- 分支分叉、认证或保护规则阻塞时是否保持现状并准确报告，没有强制推送？
- 用户明确要求公开一行安装时，本地和远端发现结果是否都与仓库布局一致？

## 交付

先说明结果现在怎样工作和用户怎样使用，再说明实际修改与核对。结构、真实内容、正式使用和远端状态分别报告；只做过哪一层就说哪一层。达到用户结果后停止。
