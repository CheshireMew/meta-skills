# Skill 最终核对清单

交付新建或修改后的 Skill 前，按顺序检查。前面的行为关卡没有通过时，不用结构完整掩盖问题。

## 0. 是否正向且提前预防

- 修改 meta-skills 自身时，是否在改动前后运行了 `scripts/quick_validate.py`？未获得核心修改授权时，受保护核心块、指纹、标题和顺序是否保持不变？
- 如果核心原则发生变化，当前用户是否明确点名授权修改核心原则，而不只是泛泛要求“优化、精简或重构”？
- 主流程是否先完整说明正常请求应该怎样成功，而不是靠连续“不要”和失败案例拼出边界？
- 从纠偏中学习时，是否找到错误发生前最早可控制的判断点，并把正确动作前移到那里？
- 从正常经验中学习时，是否有明确认可、重复选择、可观察成功或独立依据，而没有把未修改、未回复或未反对当成长期认可？
- 用户不说出历史错误时，Skill 是否仍会主动避免它？
- 活动 Skill 及其依赖中是否没有失败样本、回归案例、纠正故事、案例提示词、案例输出、案例工作区或自然语言 Harness？
- 是否没有把案例改名成正向请求、fixture、模板或默认方法后继续保存？

## 1. 用户本意是否被保留

- 是否有一份基于用户真实请求、附件和上下文的行为合同？
- 是否能用一句话说出用户最终想拿到什么？
- 吸收任务是否写清目标 Skill 当前最有价值的能力、仍然缺少什么，以及来源能补足什么？
- 领域最佳实践、仓库规则或设计者偏好是否擅自扩大了用户要求？
- 用户确认的是默认行为和示范输出，而不只是文件修改计划吗？
- 用户不需要先纠正 Agent 就能观察到的成功结果是否已经写清？
- 默认流程是否来自用户目标、稳定事实和可迁移机制，而不是单个案例中的具体答案；限定能力是否保留了价值成立所需的构成性结构？
- 来源能力有不同精度、覆盖、成本或风险层级时，是否选择了满足当前结果的最低完整层级，而不是把最高强度设为统一默认？
- 是否检查可用历史反映的上层用户结果，判断当前 Skill 职能过窄、过宽还是适当？
- 多项相邻需求形成稳定角色时，是否提出完整定位供用户一次确认，而不是要求用户逐项补充能力？

## 2. 来源、动作和停止边界是否明确

- 默认信息真源是什么？
- 外部链接、联网、安装、运行、写入、发送和删除分别在什么条件下允许？
- 用户只点名 Skill、只附加文件或没有补充问题时，默认走哪条路径？
- 第一步必须做什么？信息不足时是从现有材料确认、追问、降级还是停止？
- 做到什么必须立即交付，不再继续研究或扩张？

## 3. 默认路径与按需分支是否隔离

- 默认路径能否独立完成用户最常见的请求？
- 深入研究、实时查询、实际运行和长篇输出是否只在明确触发时执行？
- 不同输入或项目类型只有在方法确实改变时才分支吗？
- 深入分支的要求是否反向污染了默认路径？
- 强度升级是否有用户要求或可说明的结果风险，升级后证据、动作和验收是否真的变化？
- 人物、对象、动作、场景、风格、措辞和数值是否没有被一次案例直接升级为全局默认；其中定义限定能力的构成性结构与必要参数是否被保留并限制在正确分支？
- 职能范围与动作权限是否分开，避免因为扩大能力就自动扩大联网、运行、写入、发送、发布或删除权限？
- 职能缩小是否有明确排除、持续误触发、稳定冲突或职责迁移等积极证据，而不是只因为历史中没有出现？

## 4. 输出是否真的说人话

- 第一段是否直接回答用户问题，而不是介绍研究过程？
- 第一次出现术语时，是否说明谁做什么、得到什么？
- 数量、分类、目录、证据标签和抽象术语是否只是辅助，而不是答案本身？
- 是否提供了足以让普通人理解的具体场景？
- 每句话是否改变下一步动作、输出或用户理解？正确但无关的内容是否已删除？

## 5. 规则是否只有一个真源

- 会影响第一判断、来源、动作、默认输出和停止条件的规则是否都在 `SKILL.md`？
- reference 是否只保留过长模板、详细清单、领域知识或边界明确的专业能力？
- `SKILL.md` 是否写清每个 reference 的读取条件、路径和行为目的？
- script 是否只用于重复、确定且手写容易错的动作，并写清输入、输出和失败处理？
- 被替代的旧入口、旧 helper、旧类型、旧恢复逻辑和冲突规则是否已经彻底迁移？
- 职能扩大或缩小时，`description`、第一判断、主流程、reference 路由、输出和停止条件是否已经一次性迁移，没有保留两个活动身份？
- reference、script、fixture 和历史输出目录是否都没有绕过案例隔离？
- 来源中的脚本、模板、schema 和资产如果是价值因果链的一部分，是否有明确消费者并按当前任务达到结构可达、真实实例化或端到端消费中的正确等级；如果没有价值，是否没有为了完整而复制？

## 6. 行为是否经过跨表层核对

- 是否使用了用户这次真实请求或最接近的正常成功请求？
- 是否再检查了一条替换人物、对象、动作、场景、措辞和数值后的正常请求？
- 两个请求是否使用同一机制但不会得到同一个具体答案？
- 新增限定能力时，两个请求是否都证明该能力能跨内容复用，并另用一个相邻但不适用的正常请求证明不会误套？
- 是否避免用失败材料和边界请求定义默认流程？
- 两个正常请求是否还能证明建议的职能范围是连贯上层角色，而不是单次功能堆积或过度收缩？
- 普通低风险修改是否只在当前对话核对读取、动作、输出开头和停止位置，没有启动 CLI、子 Agent、新进程或完整项目重跑？
- 是否准确区分了轻量核对和实际运行，没有把规则推演写成真实复现？
- 没有真实下游任务时，是否停在结构可达并明确说明，而没有制造案例、假数据或临时项目冒充真实消费者？
- 任一临时请求不符合行为合同时，是否继续修改而不是用结构校验通过结束任务？
- 吸收后目标 Skill 是否新增或强化了可观察能力，而不只是增加“理解、选择、验证”一类通用原则？
- 是否通过反事实检查：不读来源也会得到同一结论时继续寻找专业价值；删除具体结构会损害结果时把它恢复为构成性细节？
- 只有出现外部写入、复杂产物、高代价错误或用户明确要求时，是否才升级独立验证？
- 使用额外进程前是否取得用户同意，并确保请求、输出、报告和工作区不进入 Skill？

## 7. 基础结构是否正确

- `SKILL.md` 是否存在，frontmatter 是否有 `name` 和 `description`？
- 目录名是否与 `name` 一致，`description` 是否说清真实触发场景和排除项？
- 引用路径是否存在，是否没有意外的空目录、TODO 和占位说明？
- `agents/openai.yaml` 是否由最终 Skill 定位生成，包含 `display_name`、`short_description` 和引用 `$skill-name` 的 `default_prompt`？
- 图标路径是否真实存在，依赖字段和调用策略是否能解析，更新 interface 后已有非 interface 配置是否仍保留？
- 涉及本地默认启用时，是否只有一个活动联接指向唯一源码目录，源码与联接路径内容一致？
- 被替代的系统 Skill 是否按真实绝对路径禁用，整个 Codex 配置能解析，并已说明重启和新任务验收要求？
- 是否运行 `scripts/quick_validate.py <skill-folder>`，并理解它只证明结构？
- 是否检查旧词、旧路径、旧规则和调用点残留？
- 对 meta-skills 本身，结构校验是否明确拒绝旧回归文件、Harness、用例目录和运行入口重新出现？

## 8. 返回结果是否准确

- 是否只说明关键文件和行为变化？
- 是否简要说明做了结构校验、轻量行为核对或实际运行中的哪一种？
- 涉及脚本、模板、schema 或资产时，是否说明实际达到的资源验证等级，没有把路径存在写成已经真实使用？
- 是否说明两个表层不同的正常请求完成了临时核对，但没有保存它们的原文和输出？
- 新增限定能力时，是否说明了相邻不适用请求的边界核对和目标 Skill 的可观察能力变化？
- 是否把结构检查与行为验证分开说明？
- 没有实际运行时，是否避免声称已经真实复现？
