# 交付前的最终核对

只在新建、能力迁移、复杂长期资源、高风险动作、顽固问题独立验收或仓库发布前使用。普通文字和单一路径修改不加载本清单；只检查本次实际涉及的部分。

## 使用方式

主入口已经负责用户原意、确认范围、一次实施和失败停止。本文件不再复述这些共同规则；只选择与本次高风险结果直接相关的一节。若检查暴露新的根因、输入边界、系统路线、活动资源、文件范围或验收方法，停止目标写入，把差异交回新的方案确认。

交付前先确认 `SKILL.md`、直接引用和 `agents/openai.yaml` 可读，并运行 `scripts/quick_validate.py <skill-folder>` 与 `scripts/file_budget.py <skill-folder>`。前者输出只能称为结构与 Markdown 文件预算结果，后者必须列出全部纳入门槛的活动 Markdown。修改 Meta-skills 核心或检查器时，再运行 `scripts/self-test-quick-validate.py`。

## 用户结果与开放判断

- 是否先根据结果成立方式核对：能够客观核实的结果看真实产物、状态和证据；依赖用户偏好的开放结果在用户判断前保持中性候选？
- 测试数量、字段齐全、步骤完成、参考痕迹和其它内部代理指标是否没有代替最终结果？
- 用户已经说明某个问题没有发生、不属于本次问题或不需要处理时，方案是否只据此收窄范围，没有把它带回目标 Skill 成为保持项？
- 目标 Skill 是否没有为假想风险、可能误用、一次偶发失败、追求稳妥或显得完整增加限制、例外、确认、回退或检查；保留的约束是否只来自用户明确要求、固定机器协议、真实权限或不可逆外部动作？

以下项目只在目标包含开放创作时检查：

先单独阅读最终会进入创作模型的运行提示词，再看测试、样稿和其它检查结果。

- 是否给足完整材料、完整参考和用户硬要求后，把角度、取舍、结构、篇幅、句子与结束位置交给模型，没有预写结构合同？
- 最终交给创作 AI 的实际输入是否只有一份；内部分析是否没有继续扩成创作简报、结构方案、风格合同、负面清单、评分标准或 QA 指令叠加进去？
- 写前材料净化是否只删除不适合进入创作输入的内容，保留原文、顺序、来源边界和必要上下文，没有变成摘要、写作简报或正文骨架？
- 正常工作需要的多个完整案例、钩子或风格参考能否一起进入上下文；索引是否没有取代全文？
- 目标 Skill 已经规定为不同职责或互斥集合的案例、钩子和其它参考，是否仍保持独立，没有复用同一正文或被统一索引悄悄合并？
- 完整参考是否能够按其整体内容和表达自然影响当前成品，没有因为增强参考作用而增加未经证据支持的补偿性限制？
- 最终成品是否经过实际阅读、观看或试听，语言是否自然？
- 比较创作结果时，用户判断前是否只中性展示完整结果和可观察差异，没有用每份参考是否留下可辨认痕迹等维护指标代替阅读体验？
- 如果少量删改便能保留主体选材、事实关系和推进方式，是否只处理成品，没有据此增加写前决定？
- 研究和筛选过程是否只影响取舍，没有把检索分类、排除理由和内部标签自动写进成品？

## 能力载体选择

- 是否只在用户要求比较或尚未确定实现方式时选择方案，没有覆盖用户已经明确决定的执行者、可复用包装或使用入口？
- 推荐是否从用户最终结果、实际使用频率、调用方式、精确性、状态、交互、账户、协作和持续运行需要出发，而不是默认把所有长期能力做成 Skill？
- 是否分别确定了实际执行者、可复用包装和使用入口，没有根据 CLI、API、GUI 或插件等入口名称推断背后的能力性质？
- 一次性工作是否直接完成；只需手动复用模型说明时是否交付提示词或模板；确定且必须一致的操作是否交给确定性程序并选择合适入口；需要判断、状态、交互或成熟产品能力时是否使用相应模型、Agent、软件或服务？
- 创建前是否按实际执行者、可复用包装和使用入口检查真正相关的已有方案，并根据用户结果、材料、权限、环境和持续成本判断，而不是只搜索 Skill 或按知名度选择？
- 组合方案是否只有一个清楚的主结果，每个部分各自承担不可替代的职责，没有重复维护规则、数据、状态或入口？
- 最终是否给出可以直接使用或继续实施的结果；推荐非 Skill 方案时是否已经停止创建空壳 Skill？

## 概率性结果

- 本次结论是否真的涉及稳定性、概率或候选选择；普通修改是否没有因此启动实验体系？
- 用户是否已经明确要求或批准重复采样、候选、评审或细化？
- 比较是否固定了用户原始请求或确认交接、必要材料、完整参考、模型设置、代码版本和运行方式，并且只改变待验证因素？
- 是否分别观察了 `single@1`、`pass@N`、`critic@N` 和二次细化后的改善或退化，并同时考虑事实错误、延迟和成本？
- 候选覆盖、评审选择和二次细化的问题是否分开定位；是否没有因为生成不稳定就继续堆叠提示词？
- 多候选、评审或细化如果进入正式 Skill，是否有改善证据并已经取得用户对新路由的明确同意？
- 全新上下文是否只被用于检查对话隔离，没有被当作修改有效或根因成立的单独证据？
- 真实结果失败后是否已经停止目标写入，没有换根因、换题目或继续补规则？

## 研究与分析

- 关键事实、时效和争议是否按结论风险核实；事实、推断和观点是否分得清？
- 目标 Skill 已经规定搜索用于发现信息、助推传播、核查事实或其它目的时，修改后是否仍保持原目的，没有静默改成另一种搜索？
- 来源是否真正支撑相应结论；没有影响用户理解和行动的检索过程是否留在内部？
- 直接引语、数字、日期、链接和明确归因是否保持准确；面向用户的解释是否自然？

## 程序必须读取的产物和长期资源

- 每个纳入范围的活动 Markdown 是否都不超过 9,000 tokens 的外层工具估算；非 Markdown 是否继续由实际生产者、消费者和项目验证负责，没有被提示词预算越权管理？
- 发生拆分时，用户能力、必要方法、完整示例、协议精度、公共入口、正式消费者和测试身份是否都有迁移证据；预算通过是否没有被冒充为语义完整？
- 目标 Skill 自行维护的内容是否属于其既定职能内、正常工作会读取的领域资源；触发边界、职责、路由、权限和长期规则的变化是否仍由 Meta-skills 根据用户结果和证据处理？
- 固定字段、格式、创建者、读取者和错误处理是否只有一套明确约定？
- 同一份真实产物是否从正式生成步骤进入正式读取步骤；是否没有用手写中间数据或假使用者代替？
- 需要锁定输入、哈希、代码版本、运行顺序或可复现记录时，是否由确定性程序通过合适入口承担；需要隔离模型上下文时，是否使用当前 Agent 宿主的原生任务机制，并正确区分 Codex App 当前任务内的子代理、用户明确要求的新任务和 Agent CLI 自身的会话机制？
- 本机配置、私人库或外部工具是否真实存在并被正式入口读取；示例配置和临时目录是否没有冒充就绪？
- 正式机器资源是否有稳定名称、版本、唯一正文和公开入口，并能从新的外部项目读取？
- 普通文本参考是否没有被强加机器资源才需要的登记、版本和测试？
- 结构存在、真实材料被读取和最终用户结果是否分别如实报告？

## 文件落点与运行输出

- 是否枚举了所有真正会写文件的入口，包括嵌套脚本、第三方辅助脚本、下载、日志、QA、缓存、导出和安装步骤，而不是只看主命令？
- 每类文件是否有明确所有者：Skill 源码、用户点名的目标项目、Skill 自己的本地工作区、外部数据或安装目录、缓存或临时目录？
- 生成型 Skill 的生产根是否由代码自身位置稳定解析到该 Skill 的 Git 忽略运行区；调用目录、活动仓库、输入来源、相对路径和外部交付目标是否都没有改变它？
- 只有用户结果本身是修改现有项目文件时，是否才写入用户明确要求改变的准确项目；是否没有把“在项目目录中调用”解释成点名目标项目？
- 从一个不相关 Git 仓库调用真实入口后，全部生产文件是否实际进入 Skill 自己的运行区，调用方工作树与未跟踪文件是否都没有变化？
- 用户明确要求外部交付时，是否只在 Skill 内真实结果通过后复制点名成品，并证明生产根、活动真源和保留成品仍在 Skill 内？
- Skill 私有运行产物是否处于预期的 Git 忽略状态，应该随源码分发的资源是否正常跟踪；目标仓库和调用方仓库的 `git status` 是否都已检查？
- 迁移旧产物时，源和目标是否准确、目标没有被覆盖，迁移前后相对路径、大小和哈希是否一致，内部旧绝对路径与两个仓库的 Git 状态是否已经复核？

## 能力迁移和外部材料

- 是否迁移了完整用户能力，而不只是相似文件；来源的真实材料、关键做法、使用位置和结果是否都已确认？
- 共同做法是否只临时代换了已经确认不影响结果的表面信息，并用两个表面明显不同但仍在目标范围内的对象代入后仍能自然产生同类结果？
- 规则准备进入 Meta-skills 跨类型通用层时，代入对象是否来自结果机制明显不同的 Skill；只能在当前领域成立的内容是否留在了对应的专用位置？
- 构成稳定领域身份、事实边界、专业条件、关键结构或固定协议的名称、阈值、版本和其它取值，是否继续按所需精度保留在领域规则或资源中？
- 必要差异是否继续保留为事实、边界或专业要求，没有被压成“按情况处理”，也没有被强行改造成普通请求的分流？
- 直接复用或改编的第三方内容是否追溯到准确的原始项目并按许可证致谢；独立实现是否没有虚构依赖？
- 保留项是否先接通新入口和实际使用位置；用户明确退出项是否没有被兼容或恢复逻辑带回？
- 入口已经接好、真实材料已经读到、用户结果已经产生是否没有混为一谈？

## 高风险和外部动作

- 目标 Skill 的正常运行如果包含明显耗时、算力或付费的批量工作、大量产物或重大变更，是否在真正执行前展示了具体目标、范围、输入、主要动作、产物与影响位置、成本或不可逆影响和验收方式，并等待用户明确确认？
- 权限、准确目标、影响范围和恢复办法是否在动作前确认？
- 发布、发送、删除、付费或不可逆写入后是否核对实际外部结果？
- 只有错误代价确实较高或用户明确要求时，是否才增加独立确认和更深检查？

## 仓库发布

- 目标已经配置当前跟踪远端，而且用户没有选择只改本地时，是否把提交前工作区中的全部已跟踪修改、未跟踪文件和现有删除一起验证并使用 `git add -A` 暂存，没有选择性排除？
- 暂存状态和差异是否覆盖提交前看到的整个工作区，提交后是否没有遗漏，远端最新提交是否与本地提交一致？
- 分支分叉、认证或保护规则阻塞时是否保持现状并准确报告，没有强制推送？
- 用户明确要求公开一行安装时，本地和远端发现结果是否都与仓库布局一致？

## 交付状态

结构、真实材料读取、用户结果、外部动作和远端状态分别报告。只证明哪一层就说哪一层；真实结果未通过时明确标记当前修改仍是未验证候选，并停止。
