# 交付前的最终核对

只在新建、能力迁移、复杂长期资源、高风险动作或仓库发布前使用。普通文字和单一路径修改不加载本清单。混合任务分别检查相应阶段，不能把所有条目相加成统一重流程。

## 所有任务共同检查

- 第一段是否直接回答用户问题，所有说明是否使用目标用户能理解的语言；必要专业词是否在第一次出现时解释？
- 是否忠实保留用户原意、事实、关系、详略、主次、确定程度和材料作用，没有因通俗化或内部分类而改写需求？
- 用户要得到的结果、允许动作和停止位置是否清楚；只改变了用户点名的方面？
- 改造前仍然有效的能力和长期资源是否继续有入口和实际使用位置；用户未要求退出的结果是否保留？
- 修改前后的默认动作、自动流程、固定交付、用户确认点和停止位置是否逐项一致；任何消失、降级、改成按需或权限变化是否都来自用户当前明确要求？
- 涉及创建、修改、移动、归档或删除 Skill 活动文件时，是否已经先展示具体方案并等待明确确认；是否没有把最初提出目标误当成批准方案？
- 每个主要结果是否只有一条主路径；特殊分支是否真的改变做法；参考说明、脚本和素材是否只完成主文件选定的职责？
- 新增的字段、状态、流程、索引、脚本或检查器是否有明确用户价值和正常使用者；简单方法足够时是否已经退出？
- 同义提醒、反面禁令、无人使用的记录、只证明过程的检查、旧入口和兼容做法是否已经收回？
- 当前没有入口的内容是否先检查了旧改造造成的断路，而不是直接判成无用？
- 失败输出、纠正故事、临时请求和工作区是否留在当前任务；正常工作需要的完整示例、模板和素材是否仍能被读取？
- `SKILL.md`、直接引用路径和 `agents/openai.yaml` 是否可读，`scripts/quick_validate.py <skill-folder>` 是否通过；是否明确说明这只证明结构？
- 主文件是否不超过 220 行和 14,000 个字符；如曾超出，是否通过合并重复规则和移动详细方法收敛，而不是删除能力或提高上限？

## 创作与开放判断

- 是否只固定可靠事实、用户硬要求和必要格式，没有候选计数、唯一模仿对象、评分、采用记录或过程证明？
- 正常工作需要的多个完整案例、钩子或风格参考能否一起进入上下文；索引是否没有取代全文？
- 示例中的关键组织和表达方法是否与偶然的人物、数字、名称和段落数分开？
- 最终成品是否经过实际阅读、观看或试听；事实是否可靠，语言是否自然？
- 研究和筛选过程是否只影响取舍，没有把检索分类、排除理由和内部标签自动写进成品？

## 研究与分析

- 关键事实、时效和争议是否按结论风险核实；事实、推断和观点是否分得清？
- 来源是否真正支撑相应结论；没有影响用户理解和行动的检索过程是否留在内部？
- 直接引语、数字、日期、链接和明确归因是否保持准确；面向用户的解释是否自然？

## 程序必须读取的产物和长期资源

- 固定字段、格式、创建者、读取者和错误处理是否只有一套明确约定？
- 同一份真实产物是否从正式生成步骤进入正式读取步骤；是否没有用手写中间数据或假使用者代替？
- 本机配置、私人库或外部工具是否真实存在并被正式入口读取；示例配置和临时目录是否没有冒充就绪？
- 正式机器资源是否有稳定名称、版本、唯一正文和公开入口，并能从新的外部项目读取？
- 普通文本参考是否没有被强加机器资源才需要的登记、版本和测试？
- 结构存在、真实材料被读取和最终用户结果是否分别如实报告？

## 能力迁移和外部材料

- 是否迁移了完整用户能力，而不只是相似文件；来源的真实材料、关键做法、使用位置和结果是否都已确认？
- 共同做法去掉来源专名、原句和偶然取值后，用两个表面明显不同但仍在目标范围内的对象代入，是否仍能自然产生同类结果？
- 会改变识别、判断、动作、产物、验收或停止位置的条件细节是否继续可识别、可执行，没有被压成“按情况处理”；共同做法与条件差异是否能在同一请求中按顺序共同生效？
- 直接复用或改编的第三方内容是否追溯到准确的原始项目并按许可证致谢；独立实现是否没有虚构依赖？
- 保留项是否先接通新入口和实际使用位置；用户明确退出项是否没有被兼容或恢复逻辑带回？
- 入口已经接好、真实材料已经读到、用户结果已经产生是否没有混为一谈？

## 高风险和外部动作

- 权限、准确目标、影响范围和恢复办法是否在动作前确认？
- 发布、发送、删除、付费或不可逆写入后是否核对实际外部结果？
- 只有错误代价确实较高或用户明确要求时，是否才增加独立确认和更深检查？

## 仓库发布

- 目标已经配置要推送到哪个 GitHub 仓库和分支，而且用户没有选择只改本地时，是否只暂存本轮授权改动，提交并推送当前跟踪分支？
- 暂存差异是否没有夹带其它工作区修改，远端最新提交是否与本地提交一致？
- 分支分叉、认证或保护规则阻塞时是否保持现状并准确报告，没有强制推送？
- 用户明确要求公开一行安装时，本地和远端发现结果是否都与仓库布局一致？

## 交付

先说明结果现在怎样工作和用户怎样使用，再说明实际修改与核对。结构、真实内容、正式使用和远端状态分别报告；只做过哪一层就说哪一层。达到用户结果后停止。
